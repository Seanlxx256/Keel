# Keel 和 Compass 从零入门与项目面试手册

理解原理 讲清实现 解释实验 回答追问

整理日期 2026 年 10 月 28 日

## 阅读路线与使用方法

本手册面向没有 AI 或 Agent 背景的读者。先学会“模型提出动作，程序检查并执行，环境返回结果”这条主线，再理解 Keel 怎样管理代码修复，Compass 怎样帮助定位代码，最后练习用真实实验回答面试追问。

Keel 是面向仓库级代码修复的运行框架。接入 LLM 后，它组织定位、修改、验证、审计和受限恢复。Compass 是可独立使用的代码索引、检索与上下文服务。两者均有可运行实现，但并未证明在广泛独立任务上优于成熟 coding agent。

每个主题分为原理、项目实现和面试回答。原理说明一种方法怎样工作；实现说明项目实际做了什么；实验结论说明现有证据能支持到哪里。不要把三者混成一句“全部实现并验证有效”。

建议分四遍学习。第一遍阅读第 1 至 6 章，能够画出正常与失败流程。第二遍阅读第 7 至 15 章，解释关键工程机制。第三遍学习第 16 至 20 章，掌握实验、失败和微调。最后用第 21 至 24 章进行口述与自测。

背诵不能替代操作理解。面试前至少亲自打开一份任务配置、一份 diff、一份测试报告和一次失败轨迹，并能说明它们如何对应同一次运行。没有做过的内容，应说“我理解原理，项目中尚未实施”，不要将手册中的备选方案当成个人经历。

本手册帮助准备该项目的技术面试。通用算法、编程和机器学习岗位还可能考查更广的基础，不能仅靠背诵一个项目覆盖全部要求。附录四提供初学者常用词汇，可在阅读过程中随时查阅。

## 1 先理解代码任务和基本开发术语

仓库 repo 是一个项目的代码及相关文件集合。源码实现功能；测试通过输入和断言检查行为；依赖是项目使用的其他软件包；构建是把源码准备成可运行或可安装形式。Git 用提交 commit 标记版本，PR 是提交给维护者审查的一组修改，issue 是问题或需求记录。

Bug 是实际行为不满足预期。补丁 patch 或 diff 记录修改前后差异。回归是修复一个问题时破坏了原有行为。验收则是判断任务是否满足约定的过程，可以包含目标测试、回归测试、构建和人工审查。

例如 first_item(items) 直接返回 items[0]。当输入为空列表时抛出 IndexError，用户期望返回 None。这里“空列表返回 None”是需求；异常是观察；增加空输入分支是一种候选修法；测试该输入以及正常输入，是验收的一部分。

路径是文件地址。用户指定仓库 D:/my-project，工具参数 src/parser.py 是相对路径，解析后指向 D:/my-project/src/parser.py。../ 表示上级目录；绝对路径直接从磁盘根开始。文件系统链接可能使看似仓库内的地址指向仓库外，因此还需要检查真实解析位置。

Python 解释器负责执行 Python 程序。不同虚拟环境可以安装不同版本的包。pip install 成功，只能说明包被装进某个环境，不能证明实际执行任务的解释器能够导入它。Docker 镜像是构建好的环境模板；容器是镜像启动后的运行实例。复用镜像不等于复用上一次测试成绩。

**面试回答**：仓库级修复不只是生成一个函数。它还需要找到问题在项目中的位置、理解依赖和调用关系、在正确环境应用补丁，并验证目标行为和原有行为。

## 2 LLM Agent Harness 和 Runtime

LLM 是根据输入生成后续内容的语言模型。模型参数是训练得到的数值；推理 inference 是固定参数下处理输入并生成输出。模型能生成代码和操作建议，但真正的文件写入、命令执行需要外部程序完成。

Token 是模型处理文本的基本单位，不等于一个字、一个单词或一个字节。Tokenizer 将文本编码为 token ID。上下文窗口限制单次请求可容纳的输入和输出；累计 Token 预算限制整个任务的消耗，两者不是一个数字。

工程上可以近似理解为 Agent = LLM + Harness。广义 harness 是组织模型、工具、上下文、状态和执行规则的一套程序。其基本循环是：构建请求 → 调模型 → 解析动作 → 检查并执行工具 → 返回观察 → 再决定下一步。

Runtime 强调运行中的调度、状态、预算和恢复；harness 强调模型、工具及控制机制的整合。两者没有统一的严格包含标准。本手册把 Keel 的运行控制部分称为 runtime，把整套外围程序称为 harness。“宿主程序”只是对执行模型请求的程序的称呼，不是额外的神秘组件。

工具调用是结构化请求，例如 replace(path="src/parser.py", old="A", new="B")。LLM 不决定由哪个 Python 模块接收它；开发者预先写好的 AgentSession、Gateway 和 Workspace 调用链负责分派与执行。

系统提示词规定角色规则，用户提示包含任务，工具返回构成观察。ReAct 是推理与动作交替的工作方式，不意味着必须向用户暴露完整内部思维。模型给出的解释是可审查的陈述，不是其内部生成过程的完整证明。

**面试回答**：LLM 提出动作，harness 执行动作并管理反馈。同一个模型配不同工具、上下文和结束条件，结果可能不同；但“搭了 harness”本身不能证明性能更好。

## 3 项目解决什么问题及当前边界

随着 AI 参与开发，团队需要检查更多自动生成的修改。人工审查擅长理解业务和设计，但需要时间；CI/CD 能运行配置好的测试、构建和规则，却不会在没有专门集成时自动管理 Agent 的探索、重试和预算。

Keel 将部分控制前移到执行过程：限制可写范围，管理阶段和预算，记录原始证据，在测试失败后走受限恢复路径。它支持人工和 CI，不替代它们。CI 不是“写死答案”，其他 coding agent 也可能具有类似控制机制。

Compass 帮助回答“应该看哪些代码”。它提供 Python 优先的结构化索引、关键词与向量检索、部分静态关系和紧凑上下文。Keel 回答“怎样推进修改并检查结果”。Keel 可以不用 Compass 的检索能力，Compass 也可以服务其他客户端；共享准备代码的包级依赖与是否实际调用检索，是不同问题。

| 项目 | 输入 | 主要输出 | 尚未充分证明 |
| --- | --- | --- | --- |
| Keel | 源码 任务 验收 配置 | 补丁 执行报告 验证与审计证据 | 广泛任务上的稳定优势和人工审查成本下降 |
| Compass | 仓库 查询 索引与预算 | 文件 符号 代码片段 关系与来源 | 对真实修复成功率和成本的稳定增益 |

**面试回答**：我构建了受约束的代码修复运行框架和配套检索服务，重点研究失败反馈如何真正推动行动，以及如何用独立执行证据判断结果。已有真实任务通过，但整体优势仍需同模型、同预算的受控比较。

## 4 用户使用场景和不适用场景

适合的起点是已有仓库、具体问题和可执行检查。例如修复空输入异常，保留原行为；修复依赖升级后的接口不兼容；为已有函数增加小范围选项。Compass 还适合陌生仓库导航、定义查询、理解调用方以及为其他代码助手提供上下文。

Keel 不要求 GitHub。用户可以提供本地项目、公司私有仓库或解压源码。普通 CLI 接收本地 --repo 和任务配置；任意 issue URL 自动下载、修复并发布 PR，不是默认具备的一条通用产品链。

CI 自动接管、Dependabot 后续修复、跨仓库安全补丁、几十文件迁移、第三方补丁审查和合规材料导出，都是可考虑的应用方向。不能仅凭底层模块存在，就说这些产品场景已全部实现。当前也不能宣称满足金融、医疗或车载行业的合规认证。

没有完整测试时，仍可使用构建检查、局部断言、属性检查或人工验收，但自动可信度会降低。“没有测试就完全不能使用”过于绝对；正确说法是缺少可靠成功判据时，不能承诺自动判断完成。探索性原型、审美型 UI 设计、跨语言大迁移，不是现有证据覆盖的重点。

**面试追问**：为什么用户不用现成 coding agent？

**回答**：没有证据证明用户应普遍替换现有工具。Keel 当前更适合需要可控实验、追踪失败和研究恢复策略的人。产品优势要通过修复率、人工介入次数、虚假成功率和总成本比较来证明。

## 5 一次任务需要提供哪些输入

用户或任务准备流程提供仓库、自然语言目标、验收方式、模型配置、预算与环境。模型负责定位和候选修法，不负责自行定义一套更容易通过的成功标准。用户可以选模板，不必逐项手填，但默认值仍是开发者设计的策略。

```json
{
  "mode": "agent",
  "goal": "修复空输入异常并保持正常输入行为",
  "model": {
    "provider": "ollama",
    "name": "替换为已安装模型",
    "base_url": "http://localhost:11434"
  },
  "budget": {
    "max_wallclock": 600,
    "max_tool_calls": 80,
    "max_tokens": 100000,
    "max_model_calls": 20
  },
  "acceptance": [
    ["python", "-m", "pytest", "tests/test_parser.py"]
  ]
}
```

这是配置形状示例，不是开箱即跑的完整项目。它要求仓库、测试、模型服务和依赖已经准备好，也没有开启自适应恢复或探针诊断。普通启动形式是 python -m keel run task.json --repo D:/my-project，应使用独立工作副本。

| 模式 | 工作方式 |
| --- | --- |
| explicit | 执行用户提供的工作项和具体替换 不需要模型理解任务 |
| agent | 模型通过工具调查 生成计划并编辑 |
| proposal | 给定调查范围 模型生成结构化修改提案 |
| localized-proposal | 模型先定位文件和定义 再提交受控提案 |

SWE-bench 专用入口另外接收 --task、--reference-grade、--model-config、--harness-python 和 --output。它将官方任务接入 Keel，不代表这些参数都是普通本地任务的必需项。

**面试回答**：任务描述表达意图，验收命令表达可执行检查。目标不能等同于测试全集，测试通过也只能支持其覆盖范围内的正确性。

## 6 六角色和完整执行流程

六角色是职责划分，通常串行切换，并不是六个独立模型并行讨论。Scout、Planner、Implementer 在 Agent 模式可以有独立会话；它们可以共用模型客户端。Critic 通常是结构化模型调用；Verifier 和 Auditor 主要是程序组件。

```text
接收任务与配置
  → 预检并建立工作区和记录
  → Scout 定位与取证
  → Planner 形成并校验计划
  → Implementer 修改
  → Verifier 验收
      通过 → Auditor 审计 → 成功交付
      可恢复失败 → Critic
          repair → 原范围修改
          replan → Scout 和 Planner
          stop → 保留现场并停止
```

预检可能包含凭据、Docker、配置、已有产物身份检查。普通路径配置了 JUnit 时可以先建立测试元数据基线；不是每次都自动运行整个上游测试集。SWE-bench 参考预检属于额外的准备链。

| 角色 | 核心问题 | 主要产物 |
| --- | --- | --- |
| Scout | 应该看哪里 有什么证据 | 文件与符号定位 源码片段 证据引用 |
| Planner | 怎么拆分和排序 允许改哪里 | 经校验的工作项 依赖与文件范围 |
| Implementer | 根据证据怎样修改 | 实际源码变更和操作摘要 |
| Verifier | 配置的检查实际通过了吗 | 退出码 日志 测试身份与结果 |
| Auditor | 修改和验收是否违反规则 | 范围与内容审计 可选元数据和突变结果 |
| Critic | 失败后修复 重规划还是停止 | 假设 下一项检查 恢复路线 |

localized-proposal 路径中，Planner 可能只是宿主把定位结果包装成工作项，不额外调用 LLM。普通非自适应路径的 Critic 可能仅记录失败。审计、权限错误和环境失败也不保证全部进入可恢复循环。

停止条件除成功和预算外，还包括主动停止、环境阻塞、保护规则拒绝、不可纠正的协议错误及中断。失败也应交付报告。角色流转、工作项依赖与诊断动作是三个不同层次。

**面试追问**：为什么要拆角色？

**回答**：为了明确每一步的输入、权限、输出和故障归属，便于替换与测试。会话隔离可能减少干扰，也可能丢失交接信息；需要实际比较，不能因为角色多就认为效果好。

### 用一个教学任务串起全部步骤

以下是帮助理解的假想任务，不计入项目实测。用户要求 first_item([]) 返回 None，first_item([10]) 仍返回 10，验收由项目预先提供的对应测试执行。用户允许改 src/，不允许改 tests/。

Scout 搜索 first_item，读到直接返回 items[0]，再阅读测试确认 None 的约定。Planner 提出只改 src/parser.py，宿主校验。Implementer 如果先提交了空列表返回 0 的补丁，Verifier 会报告“期望 None，实际 0”。这时是业务断言失败，不应去重装依赖。

Critic 发现已有证据足够，可以走 repair；如果不清楚调用方有没有把 None 作为特殊状态，则走 replan，补读调用方。如果配置了诊断且确有未解问题，也可运行最小探针。修正后 Verifier 重新执行目标和回归，Auditor 检查没有改测试、没有越界。通过后报告记录补丁、两轮验证和成本。

这里“模型生成补丁”“测试由谁提供”“实际命令由谁运行”“谁判断成功”分别是四个问题。把这四项分清，就不会误以为 Scout 读到报错等于自己已经写过测试。

## 7 状态机 DAG 和工具执行链

状态机管理“当前在哪个阶段，允许转向哪里”。例如验证失败后可以走恢复，未验证不能按成功结束。状态可以包含成功、失败和运行中，宿主检查非法转换。LangGraph 是可选编排实现，不是另一个模型。替换引擎需要保持状态与错误语义，不是换个库名就自动可靠。

DAG 是有向无环图，描述工作依赖。A → B 表示 B 需要 A 完成。它不同于角色状态机；Keel 的工作项通常顺序调度，有 DAG 不代表已经并行执行，也不代表有隔离并发工作区。

```text
Runtime 创建 Implementer 并传入 allowed_files
  → AgentSession 调用 LLM
  → LLM 返回工具名和参数
  → ToolGateway 检查并分派
  → Workspace 校验并执行文件操作
  → 账本保存观察
  → AgentSession 把观察返回 LLM
```

另一条 proposal 路径由模型提交提案，宿主检查、应用，不是该调用内开放所有工具。不要把工具式编辑的能力自动套到提案式编辑上。

**面试回答**：LLM 选择公开工具中的动作，程序员定义调用链和权限。动态行为在预先实现的接口内发生，模型不会自行决定拿 runtime.py 还是 workspace.py 来执行。

## 8 证据 上下文与根因判断

证据是可追溯的观察，例如某个源码版本的内容、工具返回、测试输出或探针结果。假设是对观察的解释，计划是下一步操作，模型摘要是压缩表达。四者必须区别。源码能证明当前实现写了什么，却未必证明运行时执行过某一分支。

一条可用的执行证据应尽量关联运行 ID、源码或候选哈希、输入、环境、调用和输出。哈希是内容指纹，用来检查字节是否变化；它不证明内容正确，也不证明来源绝对可信。

原始记录写入 SQLite 账本，当前会话可以接收预览和证据 ID，并通过 recall 获取后续内容。角色之间只有通过宿主允许的交接才获得相应记录，不默认共享完整会话，更不共享不可见的模型内部思维。

上下文管理要优先保留任务约束、当前失败、最新执行观察和待修改源码。先去掉重复包装，再按需取历史。源码变化后，旧行号和旧观察需要刷新。摘要中不能把“可能”变成“已确认”。完整记录留在磁盘并不意味着已经送入模型或被正确理解。

例如 save(writer, data) 调用 writer.write(data)，真实实现取决于 writer 是 FileWriter 还是 NetworkWriter。插件由配置或注册机制选择；缓存、环境变量、对象初始化状态会影响分支。静态调用图只能保守描述能解析的关系，动态情况可能需要实际执行。

**面试回答**：我区分“找到了、读到了、交接到了、解释对了、执行验证了”五层。只统计证据条数不足以衡量诊断进展。

## 9 写入范围和应用层安全控制

最大授权来自用户配置和系统策略。本轮文件集合由定位与计划提出，宿主校验；每次写入继续检查。授权不是模型每轮重新向用户申请，也不是模型说需要就能扩权。

```text
用户允许的写入根目录
  ∩ 非保护文件
  ∩ 已校验的工作项文件
  = 本轮编辑工具允许操作的范围
```

Gateway 检查角色和工作项文件白名单；Workspace 检查相对路径、仓库包含关系、真实解析路径、保护目录和硬链接等。文本替换要求 old 唯一匹配，Python 修改还需语法与现有 AST 审计。末尾比较纳入清单的工作区快照，发现声明范围外的变化则不能判为合规完成。

读过 tests/test_parser.py 可以帮助理解预期，不意味着允许修改它。重规划可以在上层授权范围内提出新文件；不能越过保护规则。内部元数据路径也受本地读取策略限制，但不能说实现了对全盘所有进程的访问控制。

应用层控制只能约束经过这些入口的操作。外部 MCP 服务或独立 shell 需要各自的权限与隔离；并发路径替换等安全问题也不能仅靠一次 resolve 宣称全部解决。声明范围控制的是文件边界，不证明每一行变更都必要。

**面试回答**：我采用受控入口的写前校验和工作区写后审计。它不是提示词约束，也不是完整操作系统沙箱；范围越界与语义上的过度修改要分别处理。

## 10 验证 审计和突变测试

Verifier 执行用户或框架指定的命令。Auditor 检查修改及报告是否满足规则。exit code 0 只代表进程按自身约定返回成功；还需确认报告存在、测试实际执行且结果满足验收。

AST 是代码语法结构。例如 assert x == 1 的节点不同于 assert True。项目用确定性分析检测被覆盖的断言删除或改写、恒真断言及常见 skip/xfail 注入。JUnit XML 提供 testcase 记录；比较真实测试项、身份和跳过情况，比只相信汇总数字更强，但报告也不是不可伪造。

突变测试临时把某个实现改错，再执行验收。如果测试仍通过，可能说明测试对该改动不敏感。Keel 的可选功能是受限的抽样，不是完整突变分析；没有合适突变候选、未杀死突变和执行异常要分别处理。恢复原始字节非常重要，中途崩溃仍有风险，应使用独立工作副本。

测试是有限的判据，不是上帝视角真值；编译通过不证明业务正确，覆盖率高不证明断言有效。审计也不能证明“绝不作弊”或所有恶意代码安全。测试被删改与真实源码缺陷导致测试失败，是不同类别。

**面试回答**：目标测试检查新增行为，回归测试检查保留行为，审计检查验收是否被削弱。三者互补，任何一个都不能单独证明全语义正确。

## 11 自适应恢复和诊断探针

自适应恢复是在失败后选择 repair、replan 或 stop。诊断则是为减少不确定性而阅读或执行检查。前者不会默认开启后者。当前可执行诊断桥要求相应的 adaptive localized-proposal 配置和受限 Docker 执行设置。

普通 Scout 本地工具默认只读，没有任意 shell 或测试写入权限。Critic 提出待检查问题；Runtime 登记 pending check；若配置了执行桥，在 Implementer 阶段入口、修改补丁之前调用专门诊断流程。模型生成探针，执行器运行，再交回实际输出。部分交接记为 Scout 证据，不意味着 Scout 自己有任意执行权限。

所谓诊断模型，通常仍是同一个已配置 LLM 的另一轮调用，不是默认接入了独立专家。diagnosis_supervision 是独立上下文的复核调用，也可能共用同一模型，不能按独立模型投票计算可靠性。

```python
# 教学探针 示例输入和函数需来自实际任务
for items in ([10], []):
    try:
        print(items, first_item(items))
    except Exception as error:
        print(items, type(error).__name__, str(error))
```

它获得正常输入与空输入的行为。捕获异常后脚本退出成功，可以表示实验完成，但不表示业务函数已修好。更有判别力的检查应说明：若 H1 成立观察到什么，若 H2 成立观察到什么，并控制输入、源码和环境。

第一轮 Scout 也可能已有用户报错、基线结果或保存的失败报告；这不说明 LLM 已经写过测试。新补丁的验收结果通常在 Implementer 修改后产生，再用于下一轮。诊断探针和长期回归测试也不是同一种产物。

**面试回答**：闭环的关键不是“写了 next_check”，而是检查被实际执行、覆盖当前未解问题，观察能更新判断，最后修改经过验收。多一段反思文字不等于多一条有效行动。

## 12 预算 上下文容量和停止条件

总预算管理整次运行，单会话步数管理一次角色工具循环，工具超时管理一个动作，局部恢复次数管理重试，外层 watchdog 管理失控执行。不同模式用到的上限不同，不能拿 max_steps 解释所有任务早停。

一次请求准入通常需要考虑：预计输入 + 输出预留 + 安全余量；再与模型窗口、单次策略和剩余总预算比较。累计用了 78k/120k 后被拒绝，可能是下一个请求预留超过剩余 42k，不等于剩余 Token 为零。

我们经历过 48,075 字节请求超过 48,000 字节自设门槛 75 字节就停止。先做无损整理，再引入软目标和有限弹性，后来改为 Token 与预算驱动。52.8 KB 只是旧 48 KB 加 10% 的工程取值，不是模型能力上限；一次成功未触及弹性区，不能用来证明这个阈值最优。

Tokenizer 比字节估算更贴近模型输入，但聊天包装、schema 和模型编码选择仍有差异。应记录计数方法，与提供方实际用量核对。输入容量、输出截断和总成本必须分别处理；不完整 JSON 不能被当成完整回复继续执行。

| 限制性质 | 合理处理 |
| --- | --- |
| 权限和证据完整性 | 阻止相关操作 不能自动放宽或猜证据 |
| 表示格式 | 可无损转换时转换并记录 不改变含义 |
| 请求容量 | 去重 分批取证 调整预留 后重新校验 |
| 用户总预算 | 范围内重新分配 耗尽则保存停止 |
| 重复或进度启发式 | 检查状态和新证据 允许的策略内换方向 |

共享单调时钟避免嵌套计时混乱，并预留最终验收和清理。进程活着不是有进展；重复打印心跳不能无限续期。Windows Job Object 和 POSIX 进程组可以约束本地后代，但终止本地 Docker CLI 不保证 daemon 侧工作全部终止。

**面试回答**：硬边界保护授权、完整性和真实容量；软阈值帮助调度。拒绝当前请求不应总是升级成终止整个任务，但任何恢复都不能自动追加用户预算。

## 13 Docker 依赖准备和环境恢复

普通 Keel Docker 验证后端通常使用用户预先准备的镜像，并配置只读挂载、非 root、网络与资源限制等。SWE-bench 则由其官方 harness 根据任务规则准备环境并运行测试，两条路径的权限和清理语义不能混说。求解、模型请求和 MCP 进程并非都被容器化。

官方任务通常涉及基础镜像、环境层、仓库实例层和新测试容器。APT 安装系统包，Conda/pip 安装解释器或 Python 依赖，再安装对应源码。固定 harness 版本不代表所有历史环境解析结果永久不变；版本漂移、插件入口变化和网络都可能影响构建。

恢复先分类：凭据或权限问题不能靠业务补丁解决；构建失败不能直接记成模型修复失败。项目已有注册的网络、兼容性与参考恢复控制器，但不是任意仓库的自动环境求解器。

依赖恢复应读取实际元数据，识别失败模块对应发行包，尽量保持 provider 锚点，仅调整相关 consumer。Matplotlib 案例中 pandas 1.5.3 是解析器在受限条件下选出的结果，不是为某个任务写死的版本答案。移除冲突插件要先检查提供者和依赖条件，不能直接关闭警告掩盖问题。

APT 缓存存在不意味着另一个构建后端命中缓存。项目后来将完成的 .deb 归档成带清单和哈希的产物，绑定基础镜像与安装命令，交给官方构建消费。实际安装日志 Need to get 0 B 才支持归档复用；元数据更新仍可能联网。

Windows 故障也要分开。一次 VHD 挂载拒绝经 Procmon 观察到 wslservice.exe 请求 Write DAC，定点补权限后手动挂载通过；这是开发者指导的主机修复，不是 Keel 自动学习。另一轮 WSL 挂起重启后恢复，不能把前次权限根因套过去，也不能据此证明磁盘损坏或 Keel 导致 Docker 停止。

**面试回答**：复用准备成果，必须验证身份并让下游实际消费；复用环境，不复用本轮成绩。环境改动要显式记录，重建环境下通过不等于原始条件成绩。

## 14 可观测性 账本和检查点

可观测性用于回答“发生了什么、卡在哪里、依据是什么”。result.json 记录汇总状态，trace.jsonl 记录顺序事件，ledger.sqlite 保存证据和模型记录；SWE-bench 运行另有各轮验证、最终评分和输入收据。OTLP 是遥测交换格式；本地轨迹支持不代表远端 Collector 上传和跨进程传播全部实现。

正式工作报告由宿主根据实际操作生成。Implementer 的摘要可以写进报告，但不能覆盖差异检查或真实失败。诊断执行完成后即保存中间结果，比等待最终模型回答合法后才提交更可靠；我们遇到过摘要列表为空、账本却已有探针执行的情况。

Checkpoint 是用于某种恢复的状态快照。训练恢复可能需要权重、优化器、步数和随机数状态；Agent 恢复可能需要代码、任务阶段和证据。保存源码后用新预算、新会话启动，是新尝试，不是精确恢复原会话。

昂贵产物的复用应检查源码、数据、实现、模型、配置和输入身份。中途更换实现要记录迁移；不要覆盖失败目录。必需结果写入失败应使运行失败，非关键遥测故障可以按规则降级，不能用遥测问题伪造任务失败或成功。

日志也可能包含源码和敏感信息，记录完整 transcript 必须考虑权限、保留期限和清理。不能保存凭据；日志多也不等于审查更快。是否减少人工排错时间，需要另行测量。

**面试回答**：持久化是可恢复的前提，不是恢复保证；内容哈希证明一致性，不证明正确性；完整轨迹支持复盘，不自动产生长期学习。

## 15 Compass 从索引到上下文

Compass 的任务是减少盲目阅读，让有限上下文更接近问题。基础流程是读取指定源码 → 提取结构 → 建立索引 → 检索候选 → 排序和组织上下文 → 返回路径、位置、内容和来源。

Python 优先的解析结合 tree-sitter 范围与 Python AST 元数据，并有明确的后端选择。函数、类、方法、签名、文档字符串和源码范围形成结构块。按语法切分可以减少截断函数的风险，但“懂语法”不等于理解所有运行语义。静态调用和导入关系存在无法解析的情况，不能伪装成完整运行图。

| 层级 | 方法 | 适合查询 | 局限 |
| --- | --- | --- | --- |
| T0 | 符号 路径或行号精确定位 | 已知名字和位置 | 自然语言问题可能没有命中 |
| T1 | BM25 与可用向量信号融合 | 关键词和语义描述 | 召回和排序可能遗漏或偏移 |
| T2 | 受限模型阅读和关系探索 | 需要进一步调查 | 更贵 且可能丢弃有用候选 |

BM25 根据词项匹配等信号排序。Embedding 将内容编码为向量，用相似度寻找语义相关项。混合检索是融合不同信号的大类，RRF 只是其中一种排名融合方法：score(d) = Σ 1/(k + rank_i(d))。k 平滑排名差异，缺失项按实现处理；RRF 不等于向量检索，也不是训练出来的神经重排器。

Code-aware 重排可以使用路径、符号、源码等证据调整结果；结构重排可以利用解析到的调用图。升级 T2 的阈值是启发式，不是校准的“模型置信度”。保留部分 T1 候选可以减少全盘丢失，但需要对照；也可能增加输出长度而影响指标。

增量索引按文件与内容身份复用未变化的提取和 embedding。新鲜度检查拒绝不匹配的索引。Embedding checkpoint 避免中断后重算，但正式发布索引仍需完整性检查。SQLite 可以保存符号、关系和索引元数据；使用向量不等于必须部署独立向量数据库。

MCP 是客户端与工具服务交互的协议。Compass 有 stdio MCP 服务与 Keel 直接集成入口，不必每次都通过 MCP；工具可用、工具已被调用、调用改善效果是三层不同结论。Serena 是独立代码导航工具和对照对象，不是 Compass 的别名；Serena 作为其后端是可研究方案，不应默认说已完成融合。

**面试回答**：我把检索分成候选召回、排序、阅读和最终证据选择。先检查相关代码有没有进入候选，再决定改召回、重排还是上下文选择，避免无依据地堆工具。

## 16 评测体系与实验设计

SWE-bench 从真实开源问题及修复构建任务，官方 harness 应用候选补丁、执行测试并解析结果。项目经典数据路线固定过 swebench 3.0.0；当前在线文档可能变化，解释历史实验时必须看冻结版本。[S01]

目标测试 FAIL_TO_PASS 检查要修复的行为，PASS_TO_PASS 检查原有行为。参考补丁预检用于确认环境有验收能力，不能算 Agent 成功。测试补丁和参考源码补丁在评分侧；原始求解树未必有新增目标测试。实际失败输出可作为反馈，但不能把参考解答送入求解上下文。

自建兼容性任务需要三个组合：旧源码+旧依赖通过，旧源码+新依赖失败，上游修复+新依赖通过。否则可能只是清理旧代码、选错提交或用例不足。HTTPX、Django、Flask-Login 等早期案例属于开发验证，部分使用局部探针，不等于完整上游验收。

| 评测层 | 回答什么 | 不能替代什么 |
| --- | --- | --- |
| 单元与回归 | 框架分支和契约是否正确 | 真实模型语义能力 |
| 协议与小烟测 | 接口 导入 保存加载能否运行 | 长程稳定性或质量收益 |
| 检索评测 | 候选和上下文是否相关 | 最终修复成功率 |
| 真实修复验收 | 任务测试是否通过 | 全部需求或市场优势 |
| 冻结重复与留出 | 波动和迁移能力 | 未覆盖任务的普遍保证 |

Precision 是返回项中相关项比例，Recall 是应找项中找回比例；行级指标以代码行为单位。Recall@K 检查前 K 项找回程度；NDCG@K 将相关性等级与位置结合。文件命中、行重叠、精确集合一致率和修复成功率，不可互换。标签来自修复区域时也未必覆盖所有合理定位。

受控比较固定模型、任务、源码、预算、环境和实现，改变待评估因素；记录实际工具调用，预先声明分母和停止条件。消融可以移除或替换组件，但一次结果差异不自动证明因果；需要重复、顺序控制和独立样本。反馈集用于开发，选择集用于挑候选，最终评估集不参与调参；按任务或仓库隔离比随机切分相邻轨迹更可靠。

基础设施不可用不是代码质量零分，也不能从报告中消失。完整报告同时列计划任务数、环境可用数、实际修复数、成功数、失败类别和成本；成功后重跑不能覆盖首轮失败。模型训练集是否包含公开任务通常不确定，因此不能只因“第一次在本机运行”就称未见任务。

**面试回答**：我首先保证评测回答的是所声称的问题，再谈分数。对照模型未调用工具时，不能把成本变化归功于该工具；同题续跑的成功不能改写原批次分数。

Compass 的两组检索数字尤其容易混淆。12 仓库、173 个抽样查询、398397 个文档，是固定数据上的 BM25 基线，查询加权 NDCG@10 10.0514%、Recall@100 29.0425%。这不是全量官方成绩，也没有测整个三级检索。[S10]

另一个三任务开发实验在 100 行上下文预算下比较：RRF T1 文件命中 47.222%、行精确率 14.333%；code-aware T1 分别 72.222%、42.667%，行召回为 3.164%。它只有 Flask、Requests、Seaborn 三个实例，不是上述 173 查询都提高了。[S11]

同一三任务中，code-aware T2 行召回降到 0.770%，调用增加；说明模型深读可能丢掉有用 T1 候选。保留 T1 前缀的离线回放在部分设置恢复召回，但输出长度也变化，未证明真实修复收益。[S12]

**面试回答**：我会同时报告负结果。它们帮助判断下一步应该修接口、证据交接、检索选择还是模型能力，而不是把任何成功都归功于新增模块。

## 18 三个适合面试展开的工程案例

### 案例一 Astropy 从反思停滞到执行证据

问题是 FITS 浮点文本过长导致注释截断。候选解决目标问题，却使 test_invalid_float_cards2 回归。模型反复说需检查，误读首次写入与后续人为破坏的顺序，还提交过注释或等价改写。

我们先核对原始轨迹，区分证据缺失、解释错误、动作空间不足和上下文准入失败。补失败调用位置、当前源码和执行桥；做同环境基线与候选对照、分块回退，缩小相关改动。探针还要核对真实导入来源，否则可能测试镜像中旧源码。更强模型改善了部分探针执行，但未自动解决全部诊断。

真实推进来自让检查执行到目标路径、把观察传给下一轮，再由模型修改和官方验收。后来 v8 及两次冻结续跑通过。上下文、模型与编排多项变化同时存在，不能把成功单独归功于 tokenizer 或某条提示。

可复述经验：形式合法不等于诊断正确；执行过探针不等于回答当前问题；基线也失败不能证明补丁完全无关，基线通过候选失败则是在控制条件下更强的回归证据。逐块回退也可能受交互影响，不总能唯一定位根因。

### 案例二 Matplotlib 24627 从环境到自主纠错

目标是 clear 后解除 Artist 父引用。先遇到 APT 下载、镜像导出、超时清理、WSL 和依赖兼容问题，Agent 尚未真正修代码。单 URL 成功不代表整批安装成功，APT 完成也不代表镜像导出完成。

我们增加有进展的有限续期、共享总截止时间、参考恢复与元数据驱动兼容调整。系统资源异常与业务失败分开记录。环境可验收后，Agent 首版补丁又在初始化路径读取未建立的 child_axes，造成大面积回归。

外层 30 分钟内还有独立 10 分钟 Agent 上限，首次验收耗尽内层时间。改为共享时间并预留最终评分后，新尝试实际走了失败→Critic→修改→再验收。随后冻结三次，2/3 通过；失败样本暴露替换文本匹配两处。新反馈提供真实匹配位置与上下文，引导模型扩展唯一匹配，而不是默认改第一处。

可复述经验：先判断失败层，再决定动作；保护规则不应为求通过而放松；预算是给纠错保留机会的调度机制，实际收益仍需多次对照。

### 案例三 Matplotlib 24026 的恢复成果交接

前期手动流程累计约 88.5 分钟，其中环境阶段约 79.5 分钟；这是那七次运行的范围，不含人工开发时间，也不是整个项目总成本。独立 APT 缓存与官方 Docker SDK 构建不共享，导致正式构建重下载后再次失败。[S08]

后续加入注册恢复控制器、归档桥接和准备成果发现，绑定基础镜像、安装命令和包清单。一次开发错误把多行 Python 直接嵌进 Dockerfile RUN，得到 unknown instruction: import；改为独立脚本 COPY 后运行，并补生成产物检查。

归档桥后来实际传递 389 个包、439051774 字节。新集成运行从允许目录发现匹配成果、重新参考验收、自动交给原任务 Agent，约 740 秒完成，4 次模型调用，全部指定测试通过。[S09]

可复述经验：产物必须可发现、可验证、可消费；恢复后的状态不能在下一阶段丢失。这是使用预先准备成果的端到端执行，不是从零无人介入自愈，也不是 RSI。

## 19 从运行记忆到外层改进

项目有四种容易混淆的积累。开发文档供人和开发助手复盘；任务账本保存本次执行；操作经验库可在显式配置后提供适用建议；模型微调真正改变参数。文件越来越多，不自动等于系统越来越聪明。

一条经验应包含触发条件、平台和版本、原始证据、适用与不适用条件、可执行恢复方式、本次复验要求及历史失败。检索到经验只能形成候选，不能代替当前测试。先按错误、阶段和工具精确检索，未必一开始就需要向量库。

外层改进关注下一版系统：冻结父版本 → 模型提出少量通用提示或策略候选 → 隔离运行 → 比较质量、回归和成本 → 保留旧版或暂留候选。当前 MVP 允许生成受限指导语，不能改固定探针、标签、权限和预算，也不会自动发布生产版本。[S13]

已有结果并非一直提高。初轮曾暂留 grounded_checking，后续验证保留 incumbent；反馈回放又暂留 diagnostic_probe_precision，仍未生产推广。能够拒绝候选是有用流程结果，但不是已经持续提升的证据。

原稿讨论的外置假设账本、问题 open/resolved 状态、执行覆盖门槛、自动 delta debugging、异模型军师、MCTS 等，应作为设计或待验证方向。不能将建议的 schema 和伪代码整段当作现有统一实现。到达某个栈帧也只是相关性代理，不充分证明实验有判别力；固定动作菜单同样需要验证。

RSI 研究提供可检验改进循环的启发。Terminal-RSI 交替使用验证轨迹改写与策略精炼，其训练 Critic 是价值网络，不等于 Keel 的提示词 Critic。ECG-RSI 将编辑后重测量、错误反馈与独立选择分开。借鉴重点是“提案不等于有效，独立比较决定保留”，不是照搬完整训练算法。[S16 S17]

**面试回答**：运行中根据反馈改代码属于任务适应；保存可检索经验属于系统记忆；改变提示和工具属于脚手架改进；更新模型参数属于训练。当前不能将这四种能力合称已实现完整 RSI。

## 20 Scout 微调从数据到结果

原稿早期“没有参数训练”已过时。现在已经在 RTX3050 Laptop 4GB 上开展真实 Qwen3-0.6B LoRA 训练，但没有训练外部 GPT 模型，也没有把实验适配器升级为默认 Scout。[S14 S15]

选择 Scout 是因为其文件/符号选择输入输出更窄，较容易核对来源和权限。初次审计有 61 份轨迹、207 个去重候选，但大量集中在同一任务；结构合法不代表选中符号在语义上正确。分页动作不当最终标签，同名方法可能属于错误类。原始不合格回答被保留或暂缓，不能手工修成正确答案再冒充模型标签。

批准数据由 4→6→8→15 条增长，最终 8 条文件与 7 条符号记录，来自 8 个任务、3 个训练仓库；仍是小且已暴露的开发集。后面的 7 条符号查询与每条 4 个展示产生 28 条记录，不是 28 道独立题。按仓库和任务隔离，不能把相邻轮随机切分伪装成独立评估。

SFT 用示范输入输出监督模型。生成式训练一般只对目标回答计算损失；提示、工具上下文等应按模板正确屏蔽。LoRA 冻结基础矩阵 W，学习低秩增量 ΔW=(α/r)BA，减少可训练参数和优化器状态，但不会消除长序列激活占用。[S18]

本地研究使用 q_proj/v_proj、rank 4、alpha 8、dropout 0、学习率 1e-4。生成式 LoRA 约 57.3 万可训练参数；后续候选评分增加约 1025 参数的打分头。用平衡 BCE 学习教师成员关系，最终固定 0.5 阈值、最多 8 项；没有用真实正确数量作为推理时 oracle。

候选打分与生成式输出不同：前者在候选表示上预测分数，后者生成路径或 ID。排列增强检验模型是否只记住展示编号；去编号研究减少 ordinal 文本干扰；完整目录后读出检验更完整输入是否有帮助。改变序列同时改变长度和计算，不能称纯粹的单因素可见性因果实验。

| 表示 | 训练展示精确集合 /28 | 新目录展示精确集合 /14 |
| --- | --- | --- |
| 编号 候选末尾 | 12 | 3 |
| 去编号 候选末尾 | 23 | 4 |
| 编号 分组目录后 | 8 | 1 |
| 去编号 分组目录后 | 9 | 4 |

新目录仍是 7 个已知查询的 14 次展示，不是 14 个新任务。去编号末尾组排序更好：新展示 9/14 正负完全分开，最终集合却只有 4/14 正确，说明排序与阈值选择是不同瓶颈。不能在这 14 条上调阈值后又报告独立收益。

完整比较新做 336 次更新、140 次评分前向，复用经身份核对的控制组；新运行约 1590 秒。完整目录后读出未带来最终选择收益。等更新数不等于等 Token/算力，旧组与新组机器状态也不同。

工程困难包括 CUDA 分配失败、系统提交内存不足、D 盘空间和环境导入超时。显存、主机提交内存、磁盘分别记录；释放反向图、分组减少重复路径、调整阶段预算、归档中间 checkpoint 和用户调整分页文件后完成实验。不能把所有改善单独归因于分页文件，也不能认为一次反向烟测证明全程稳定。

**面试回答**：我完成了来源审计、监督训练、严格保存加载和表示对照，发现训练拟合与排列泛化存在差距。当前证据支持开发集上的改进和明确负结果，没有证明独立修复率提升。DPO、RLHF 和 Actor–Critic 强化学习尚未实施。

## 21 高频面试问答

### 1 用一句话介绍项目

我实现了面向仓库级代码修复的 Keel 运行框架和 Compass 检索服务，重点研究受限执行、失败证据交接与独立验收，并通过真实任务、冻结回放和组件对照检查效果。

### 2 你的创新在哪里

我不把角色、Docker 或预算本身称为独有创新。项目价值是把执行、取证、恢复和验收组织成可研究的系统，并修复阶段之间的真实断点。是否优于现成系统，需要同条件基线和独立任务证据。

### 3 为什么不是简单套 API

除了模型请求，还实现了文件和工具权限、状态与依赖管理、反馈提取、来源绑定、执行控制、环境恢复和结果审计。但复杂度不是优势证明，仍需解释每个机制解决什么问题、怎样验证。

### 4 为什么不只用一个很长的提示词

提示不能代替实际权限和执行器。Astropy 轨迹中字段完整仍误读，next_check 合理仍未执行。应把可程序化条件放进程序，把需要语义判断的部分交给模型，并保留真实环境反馈。

### 5 六个角色是不是六个 Agent

当前主要是串行职责分工，模型调用可共用配置，Verifier/Auditor 是程序。部分角色有独立会话，但不是六个常驻独立模型并发协商。更准确称多角色 Agent workflow。

### 6 为什么 Critic 也会错

它也是模型调用，不是训练中的真实价值函数或客观裁判。它可能与原模型共享盲点。复核只能增加证据检查，不能代替真实探针和验收；多个模型也不保证消除相关错误。

### 7 怎么证明没有改测试作弊

我能说明声明范围、保护路径、AST 和可选报告审计覆盖了哪些行为，并出示差异和测试记录。不能证明所有绕过方式都不存在，更不能用通过测试反向证明没有作弊。

### 8 验收是谁定义的

普通任务由用户或团队配置，SWE-bench 由其任务与 harness 定义。我实现适配与反馈，不让模型自行改成功判据。测试内容和目标需求仍可能不完全一致。

### 9 为什么需要参考补丁预检

先判断环境是否能够有效评分。参考也失败时，不能把问题都记成 Agent 修复失败。参考成功只证明该条件下可验收，不证明求解器成功；参考源码补丁必须隔离。

### 10 依赖都固定了为什么还失败

固定一个入口版本不等于所有传递依赖、系统包和外部服务固定。要保存解析结果、镜像身份和恢复策略，重新验收，不能把改变条件后的成功标作原条件成绩。

### 11 重试和恢复有什么区别

重试通常在相同条件重复动作，适合短暂故障；恢复应根据证据改变状态或策略，再验证并接回任务。错误不变且输入不变的重复调用不应无限持续。

### 12 如何避免无限循环

共享总预算、局部恢复和重复保护提供兜底。进一步区分新证据、源码变化和测试变化，再决定继续或换方向。现有停止保护不代表已经有完美的进展评估。

### 13 为什么时间还剩却停止

可能达到调用数、Token 预留、上下文、局部恢复次数、权限或显式 stop。必须报告具体限制与剩余预算，不能把所有错误都写 budget_exhausted。配置之间还可能存在不合理的嵌套上限。

### 14 怎样解决上下文太长

原始证据完整落盘，当前输入去重并优先保留最新失败、源码与约束；按需读取旧资料，使用 tokenizer、输出预留和总预算联合准入。不要盲目裁掉关键证据，也不要无限抬高自设门槛。

### 15 模型推理过程能观察吗

可以观察请求、可见解释、工具动作和环境结果，不能把显式解释当成模型内部完整因果过程。复盘根据可观察行为提出并检验原因，不推断模型故意逃避或欺骗。

### 16 Compass 和 RAG 有什么关系

Compass 可以承担代码 RAG 的检索和上下文组织部分。RAG 的关键是推理时获取外部信息，不必训练模型；代码结构、版本新鲜度和上下文预算是仓库场景的具体问题。

### 17 混合检索就是 RRF 吗

不是。混合检索组合关键词、向量或其他信号，RRF 是一种按名次融合的算法。还可以有加权分数、学习重排等方案，项目实验要明确究竟改了哪一层。

### 18 为什么向量检索不一定更好

精确标识符、路径和错误文本常适合关键词。向量可能找语义相近但实现无关的代码；结构信号也可能有解析缺口。需要匹配查询类型，并报告真实候选与标签覆盖。

### 19 T2 为什么反而变差

模型可能把有用 T1 候选过滤掉，上下文和阅读预算也可能限制选择。三任务里观察到更高调用却更低召回，因此保留便宜基线，先检查选择行为，不能把升级次数当质量指标。

### 20 Serena 节省 47% 是项目整体收益吗

不是。它是两个完整配对任务中的累计 Token 差异，并且工具组真实调用了 Serena。不是大规模因果结果，也不是 Compass 成绩，不能省略样本范围和实验策略差异。

### 21 你的学习机制会自动越用越强吗

不保证。记录、经验召回、脚手架选择和参数训练是不同层。需要验证经验适用性、版本失效和独立收益；外层候选可以被拒绝，当前未自动推广生产。

### 22 为什么微调 Scout 而不是整个 Agent

定位任务输入输出较窄，能核对源码、候选和权限，适合建立小规模训练链。它仍可能选错调用路径；训练只覆盖该子能力，不意味着端到端修复能力随之提高。

### 23 LoRA 为什么省资源

冻结基础权重，仅训练低秩增量，减少梯度和优化器状态；但前向、激活和长输入仍占资源。需要看真实最长样本、反向和优化器步骤，不能只看参数量估显存。

### 24 checkpoint 包含什么

取决于恢复目标。推理只加载适配器与头可能足够；严格训练续跑还要优化器、随机状态、步数和输入策略。只有源码快照不能恢复原模型会话。

### 25 如何排除数据泄漏

绑定时间点源码和请求响应，隔离参考补丁和未来反馈，按任务及仓库分区，去重相邻轨迹，标明历史暴露。无法证明基础模型从未见公开题时，不声称绝对未见。

### 26 训练 loss 降了能说成功吗

只说明对训练目标拟合改善。还要检查 JSON、契约、精确选择、排列稳定性、独立任务和最终修复。教师加权 NLL 下降也不等于实际输出正确。

### 27 排序正确为什么答案仍错

阈值可能选多或选少，最多八项也会改变集合。把排序与集合决策分开评估；用训练侧选择校准，再冻结到新数据验证，不能拿评估集调出好看结果。

### 28 怎样证明恢复机制有用

同模型、同任务、同环境和预算，比较关闭与开启恢复；保留所有计划任务和故障，重复运行并报告成本与人工介入。首轮直接通过的任务不能作为恢复分支起效证据。

### 29 最难的问题是什么

不是单一业务 Bug，而是信息、动作和验收之间的断点：建议未执行、输出被截断、候选源码导入不对、缓存未被消费、时间没留给纠错。需要分层对照，而非不断加提示词。

### 30 下一步优先做什么

冻结较强版本，在预先保留的新任务上验证稳定性；对 Compass 做真实调用的开关对照；对微调候选做训练侧校准与独立评估。先证明收益，再扩展模型、角色和产品场景。

### 31 SFT DPO RLHF 有什么区别

SFT 根据示范回答学习；DPO 利用偏好成对回答直接优化相对偏好；RLHF 是利用人类偏好等反馈进行强化学习的一类流程，具体实现可能涉及奖励模型和策略优化。它们都不同于在提示里要求模型反思。Keel 当前做了监督与 LoRA 研究，没有实施 DPO 或 RLHF。

### 32 LoRA 和量化有什么区别

LoRA 改变训练参数化方式，量化降低权重等数值的表示精度；可以组合，但不是同一技术。本项目不能因为低显存训练就自动称 QLoRA，需要以实际加载与训练配置为准。

### 33 为什么只训练回答 Token

生成式 SFT 希望模型学习在给定提示下如何回答，而不是把用户提示也当需要预测的目标。模板分词后构造监督掩码，提示部分通常不计损失；边界错位会让训练目标错。候选打分头的成员分类目标则不是同一套回答 Token 损失。

### 34 BCE 和 NLL 能说明什么

BCE 是二元分类损失，用于衡量候选成员概率与标签的差距；NLL 是负对数似然，用于衡量模型给目标序列的概率。损失下降支持更好拟合对应目标，不直接保证 JSON 合法、集合正确或修复通过。

### 35 怎么公平比较几个策略

固定可比输入、标签与配置，预先声明预算、顺序和评价指标，保留失败并重复。等步数不等于等计算，等上下文上限不等于实际输出长度相等。报告这些差别，而不是仅展示一个平均值。

### 36 多次重复为什么还不能证明泛化

同一任务重复测量输出波动和流程稳定性，新展示主要测表示鲁棒性。新任务或新仓库才更接近迁移问题；仍需要防止开发暴露、选择偏差和基础模型数据污染。

### 37 怎么减少缓存造成的实验误判

区分模型缓存、读取缓存、下载缓存、构建镜像和评分缓存。复用前核对其身份和适用条件；判断是否命中要看实际消费者日志，不只看目录存在。按协议重新执行最终测试。

### 38 军师和监督有什么不同

监督可以核对现有主张与证据，军师设计更偏向提出替代问题定义和实验。两者都只能提供候选意见。当前没有默认异模型陪审团；增加一个调用也可能增加成本和相关错误。

### 39 如何防止经验库误导

保存来源、版本、适用范围和失效条件，区分建议与验证事实。经验不能覆盖权限和成功判据。用开启关闭经验的独立对照，记录误导、无收益和成本，并允许撤回经验。

### 40 为什么不先做 MCTS 或更多 Agent

搜索和并行角色可以扩大探索，但会增加分支成本，而且仍依赖有效的评估信号。先保证动作可执行、证据能交接、测试能判定；否则只是同时放大多条无效路径。当前没有实现通用 MCTS 修复搜索。

## 附录四 初学者术语速查

### 代码与执行

函数：接收输入、执行操作并可能返回结果的一段代码。类：描述对象数据和方法的定义；对象：某个类的具体实例。方法：通常依附于对象或类的函数。符号：函数、类、变量等在代码中的命名实体。签名：函数名、参数和返回标注等接口信息。

调用方 caller 是使用某个函数的位置，被调用方 callee 是执行的目标。导入 import 让程序访问模块。模块通常对应 Python 文件或可导入单元；包组织多个模块。静态分析读代码而不执行；动态检查运行代码并观察。

API 是约定的调用接口，不一定联网；HTTP API 才常指网络服务接口。JSON 是结构化数据格式，schema 描述允许的字段、类型和取值。stdout 是标准输出，stderr 是标准错误流；报错也可能写到 stdout，不能只读取 stderr。

Traceback 是异常的调用栈，能定位执行经过的位置；断言 assertion 检查某个条件，失败会产生测试失败。Fixture 是测试所需的初始化环境或数据。单元测试测小组件，集成测试测组件之间的交互，回归测试检查旧行为是否被破坏。Smoke test 是快速检查基本链路能否运行。

### 模型与训练

参数是模型学习的数值；超参数是学习率、轮数等训练设置。前向计算产生表示、分数或预测；损失 loss 衡量训练目标的偏差；反向传播计算梯度；优化器依据梯度更新参数，AdamW 是一种常用优化器。

Batch 是一次处理的一批样本；step 在本手册训练语境中主要指一次优化器更新；epoch 是遍历训练数据一轮。展示增强让同一个逻辑查询以不同编号或排列出现，它增加训练记录，不增加独立任务数。

Transformer 是一种使用注意力等结构处理序列的网络。因果语言模型通常只能关注当前位置及之前的 token；因此候选末尾读出看不到后面的目录。Hidden state 是中间向量表示，readout 是从选定位置取得表示供打分。q_proj 和 v_proj 是注意力中的查询和值投影，LoRA 可以加在这些矩阵上。

梯度检查点通过重算部分前向减少保存的激活，通常以更多计算换取显存。显存是 GPU 存储；主机内存是系统 RAM；提交内存反映操作系统承诺给进程的内存；磁盘保存文件。分页文件帮助系统提交额度，不等于增加 GPU 显存。

过拟合是对训练数据表现好但迁移不足。校准 calibration 在这里指训练侧选择分数到集合的规则，不意味着模型概率已经严格校准。Oracle 是评测时人为提供的正确答案或额外真值，只可用于诊断上界，不可混入普通推理冒充自主结果。

### 系统与评测

白名单列出允许项；ACL 是访问控制列表。沙箱限制执行环境，但隔离强度取决于具体实现。哈希是内容指纹。幂等指相同操作重复执行不会继续改变结果，实际恢复仍要核对中间状态。退避 backoff 是重试前逐步等待。Watchdog 是监督超时并采取终止措施的外层控制。

遥测 telemetry 是运行状态数据，trace 是按事件记录的执行轨迹；OTLP 是传输遥测的一种协议。检查点 checkpoint 用于恢复指定状态；收据 receipt 记录产物来源、配置和校验信息。

Baseline 是对照基线，incumbent 是当前保留方案，ablation 是移除或替换组件的消融，holdout 是不参与调参的留出数据。Precision 关注返回结果的相关比例，Recall 关注相关结果找回比例，exact match 要求整个目标输出一致。RSI 指递归自我改进研究方向，不是日志积累的别称。

## 附录五 工具对照与研究方向

原稿涉及的外部项目需要分清“接过并测过”与“研究过但尚未接入”。名称只用于解释技术取舍，不证明项目当前具有对方全部能力。

| 对象 | 在本项目中的用途或拟议用途 | 应怎样表述 |
| --- | --- | --- |
| Serena | MCP 代码导航与配对对照 | 已有实际调用记录 收益限于具体实验 |
| CocoIndex | 语义代码检索适配与比较 | 已有检索评估 不等于完成业务修复 |
| Aider | 紧凑 repo map 和排序的参考或组件对照 | 不能把组件分数当完整 Agent 表现 |
| Continue | 候选 重排和回退分离的参考 | 研究借鉴不等于代码已融合 |
| SWE-ReX 与 mini-swe-agent | 受控执行层和简洁循环的拟议参考 | 不声称当前主流程已替换成它们 |
| Context7 与 uv | 版本文档取证和依赖管理的备选方向 | 不声称已自动获得所有文档或锁定全部依赖 |
| RepoHyper 与 Qwen Embedding | 图检索与神经检索的研究候选 | 不应当成已测出的项目收益 |
| Docker MCP Toolkit 与 Skills | 工具服务管理或调查流程规范的思路 | 工具启动和提示流程不能代替缺失的恢复操作 |

有一组三任务导航对照，在 100 行上限下，Compass 历史配置、Serena 适配、CocoIndex 语义配置的平均行召回分别约 3.16%、4.09%、1.69%。实际输出长度、策略和时序有差异，标签还包含宽区域；不能据此宣布某工具全面胜出，更不是三者修复成功率。[S19]

原稿还提到树或图搜索、Beam Search 和 MCTS。它们尝试维护多个候选路径，通过评价和剪枝分配计算。难点是分支成本与评价函数可靠性；当前项目没有实现通用多分支修复搜索。外置假设账本、动态停滞切换和异模型顾问也需要独立准入，不是因为建议合理就算完成。

阅读 Terminal-RSI 时，RSR 表示对验证轨迹改写后用于监督更新，RPR 表示策略精炼；TB-GAE 关注按交互回合组织信用分配、避免冗长观察稀释决策信号；FDR 与 SPR 是不同的奖励设计。信用分配要回答“哪次动作对最终结果有贡献”。奖励重分配的占比变化不能当作任务成功率变化。这里只保留方法启发，Keel 未实现这些训练机制，也没有复现论文结论。[S16]

ECG-RSI 的启发是编辑后重新测量验证、根据学习者错误提方案，再在独立选择集比较。迁移到 Keel，应先构造可实际执行的故障案例，验证故障确实出现，再比较少量候选。不能只让模型描述一个故障，就把它当真实标签；也不能把反馈集改善当外部能力提升。[S17]
