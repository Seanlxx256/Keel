# Typed guard recovery: first rollout

`keel/guard_recovery.py` defines incidents by code, category, protected purpose, allowed actions and facts. `GuardViolation` retains its typed incident. This is a small shared foundation, not automatic classification of arbitrary exception prose.

Two adapters are integrated into the offline outer-improvement evaluator behind `--recover-guards`:

1. **Host candidate identity.** Model names are display metadata. A deterministic safe internal identifier (position plus name hash) is generated, the full original name is saved in `candidate-identities.json`, and guidance is unchanged. Paths are formed only from host identifiers. Even a path-like display name cannot select a filesystem location. Duplicate names remain ambiguous and are rejected; unknown configuration fields remain forbidden. Metadata has a 16KiB resource envelope, guidance and candidate-count limits remain; this does not solve every arbitrary size restriction.
2. **Unknown observation citation.** The attempted action remains rejected and no tool runs. If all other fields are valid, the executor returns a typed event with available real observation IDs and allowed choices. The model may propose a new action, withdraw the claim or choose a valid probe. There is at most one such correction per trial and it consumes the existing three-turn/shared budget. A repeated bad citation, exhausted call/time budget, malformed structure or illegal probe does not gain retries. No citation is guessed, remapped by similarity or automatically accepted.

Raw replies, rejected steps and typed events stay in trial artifacts. `guard_events` reports interception events separately from terminal protocol failure and final grounded success. A correction is not itself a successful diagnosis. If the next request cannot fit the remaining token budget, ordinary budget admission still stops it; the adapter does not expand budgets.

The new mode is recorded in the implementation/input manifest. Historical scores are not rewritten; changed recovery opportunity makes direct old/new rates a changed-protocol comparison. Explicit pre-trial proposal migration can switch the mode while retaining original raw response, protected inputs and prior usage; the old mode and implementation are recorded. Completed ordinary resumes still require exact manifest and identity mapping agreement.

Validation: 24 related tests passed (15.348s). Tests exercise a rejected citation → new valid action → real isolated fixed probe → grounded conclusion in the original three turns, repeat/no-budget/illegal-tool negatives, long metadata reaching actual comparison without another proposal call, preserved display/guidance, and completed resume without provider dispatch. These use scripted providers, not live LLM reasoning.

Historical replay evidence: `.keel/repair-review/guard-recovery-replay-v1/report.json`. It reuses the exact first rejected response from pilot-v1/case-4-incumbent, then scripted corrective turns execute two real counterfactual child probes and pass. The actual failed 26-character proposal is also mapped with guidance unchanged. Provider calls=0, Docker calls=0. This establishes the recovery control path; it does not establish that a live model will choose the correction or improve independent task success.

Not yet integrated: proposal token admission/repacking, output truncation recovery, source-range/search recovery, production six-role runtime and broader guard coverage. Existing safety/hash/test verification rules are unchanged. Next extend typed incidents to token admission with exact binding-constraint metrics and bounded safe repacking before attempting a paid efficacy comparison.

## Token admission recovery in production proposal calls

This followup extends beyond the initial offline adapters. Production `proposals._propose_once` uses shared `context_budget.admission_with_recovery` whenever a proposal token policy is configured. Add `"recover_capacity": true` to the **existing** policy to enable bounded deterministic repacking; retain its model window, per-call limit, byte ceiling, output allowance and safety reserve. Missing/false keeps repacking disabled. No new tokenizer assets are downloaded, and failed configured offline tokenizers remain visible conservative fallbacks.

Every token rejection now includes the estimator, reserved input/output/safety, actual spent/remaining tokens, call/time counters, policy identity and all binding constraints. Actual token/call exhaustion remains `BudgetExceeded`; an oversized next-request reservation with budget still available is `InputCapacityExceeded`, including when it is the global remaining allowance that the present request cannot fit. This corrects the prior conflation of reservation failure with actual depletion. The existing bounded recovery controller can pass the typed incident to model-based source selection; its calls still require shared admission and existing recovery permission checks.

At most two deterministic operations are tried, each re-admitted against unchanged constraints:

1. Compact JSON layout in user payloads. All parsed values, source indentation and line endings inside strings remain intact.
2. Apply the already registered exact duplicate execution-wrapper compactor to the proposal goal. Child output remains present in the probe object. Distinct outputs, current source windows, failure context and permissions are retained.

No automatic output reduction, changed safety reserve, learned threshold expansion, arbitrary evidence deletion or total budget increase occurs. Original messages/schema and typed incidents are required ledger checkpoints before repacking; hashes and dispositions are traced. A checkpoint failure propagates before provider dispatch. The independent byte ceiling remains checked. No-progress/continued failure stops deterministic attempts; per-request capacity may enter the existing bounded evidence-selection route, while real budget exhaustion does not.

Validation: 94 related tests passed in19.041s. A real Workspace test first proves the original request is rejected, then verifies repacking preserves original source evidence and child results, admits one scripted provider call, validates the proposal and writes the expected file. Additional tests cover global-reservation classification, immutable source/JSON, no budget charge during repacking, true exhaustion/no retry, checkpoint failure, bounded failed repacking and typed feedback reaching the existing selection route. The previously named global-depletion regression had spent zero tokens and supplied an oversized request; it now tests actual depletion by explicitly spending its allowance, with a separate test retaining the reservation distinction.

No live provider, Docker or new SWE-bench acceptance was run. Coverage is currently the policy-enabled production proposal path; generic Scout/Critic admission, diagnostic byte ceilings and truncated-output recovery are not all integrated. Historical runs cannot be reclassified as successful from these tests. Follow up with a frozen real request replay before any broader paid acceptance claim.
