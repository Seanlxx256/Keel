# Keel 面向多用户与多 Sandbox 的复用设计

## 1. 产品边界

Keel 内置六角色 Runtime 是一种执行器，不应成为接入其他 Agent 的前提。
可复用核心应负责身份、授权、预算预留、操作收据、任务租约、结果核验和不确定状态。
外部 Agent 可以使用自己的规划循环，但必须经过可信执行入口才能获得强制治理。

仅接入事后日志属于观察模式；接入前置授权属于协作模式；所有模型、工具和沙箱出口
由独立可信组件控制，才可能达到强制模式。是否真的无法绕过，还需要网络、凭证、
文件系统和进程隔离验证。不能把 SDK 回调或 MCP 接入自动称为安全边界。

## 2. 现有实现的扩展障碍

| 当前实现 | 多副本场景的问题 | 目标改造 |
|---|---|---|
| governance.ControlStore 直接使用 SQLite | 单库写入竞争，SQL 与业务逻辑耦合 | 按业务原子操作提取存储接口，再提供 PostgreSQL 适配 |
| broker 的进程内 Semaphore、active 字典 | 每个副本只知道自己的容量和执行器 | 共享资源预留、持久化归属、心跳和对账 |
| controller 绑定本地仓库路径 | 远程 Sandbox 不一定拥有该路径 | 工作区/源码版本引用，受控下载与哈希核验 |
| 本地证据目录和分页读取 | 控制端迁移后文件可能不可达 | 对象存储保存大产物，数据库保存授权和内容清单 |
| write broker 本机文件锁 | 无法约束另一主机的写入 | 每次尝试独立工作区，按租约代际校验执行与结果提交 |

不要同时重写已经通过的 Runtime：保留现有实现作为兼容后端，用同一契约测试约束新适配器。

## 3. 插件接口应围绕职责定义

以下是拟议接口，不是当前可直接调用的 Python API。

| 接口 | 核心操作 | 不可被插件自行弱化的约束 |
|---|---|---|
| AgentAdapter | 提交任务、获取动作、接收结果、停止 | 明确可拦截的出口及无法控制的旁路 |
| ControlStore | 原子预留、结算、领取、续租、提交结果 | 租户隔离、幂等键、代际条件、不确定用量保留 |
| ArtifactStore | 上传、核验、下载、列出清单 | 租户授权、哈希、大小、保留期和未完成上传状态 |
| SandboxBackend | 准备、启动、观察、停止、查询 | 明确执行身份与限制，区分停止请求和停止确认 |
| Scheduler | 准入、选择任务、预留容量、释放 | 公平性、容量原子性、不可依据单次超时释放未知资源 |
| AcceptanceRunner | 接受源码引用和固定验收契约、返回证据 | Agent 不可修改契约或以自己的文字代替通过结果 |

插件由管理员安装和注册，版本与配置摘要写入任务；任务请求只选择已授权的插件别名。
禁止根据用户传入的任意模块名导入控制端代码。插件失效必须有显式错误语义，不能静默回退到弱隔离后端。

## 4. 一个外部 Agent 如何接入

用户提交任务后，控制面分配 tenant_id、task_id、attempt_id 和初始租约。
AgentAdapter 将业务任务交给外部 Agent。执行模型/工具前，由可信代理核对授权、预算和操作标识；
执行后保存原始收据。补丁作为产物提交，独立验收读取指定源码版本和固定测试契约。
用户查询结果时按租户检查权限，而不是凭猜中的对象路径读取日志。

如果外部平台只有最终结果 API，就先实现结果导入与独立验收；不能声称能管住其内部工具调用。
如果平台支持前置工具拦截，再逐步接入控制；没有可靠拦截就使用受控 Sandbox/出口代理，或保留为观察模式。

## 5. SQLite 并发与 Pod 持久化是两件事

当前 ControlStore 使用 synchronous=FULL、BEGIN IMMEDIATE 和两秒锁等待；未显式启用 WAL。
这提供同主机事务机制，不等于多副本、高可用或磁盘故障恢复。

单机阶段：缩短事务，数据库事务内不运行模型或 Docker；分离高频可丢遥测与必须写入的账本。
WAL 可以改善读写并发，但 SQLite 仍只有一个同时写入者，不能用增加线程解决写锁争用。
应用侧写队列可以平滑峰值，但队列本身若只在内存中，崩溃会丢数据；必须定义何时才返回持久化成功。

容器可写层不是可靠持久化位置。emptyDir 可以跨同 Pod 的容器重启保留，但 Pod 删除后数据消失。
单写入服务可以将 SQLite 目录放在有持久化语义的卷上，并备份；数据库、journal/WAL 等必须位于同一受控目录。
存储类、卷回收策略、节点故障后的重新挂载、备份与恢复都需要单独验证。
PVC 不会自动提供数据库复制、租户隔离或应用层高可用。
不能让跨主机的多个 Pod 通过共享 NFS 直接并发打开 WAL 数据库。

生产多副本：控制面使用 PostgreSQL 等独立事务数据库保存权威状态；Sandbox 本地 SQLite
可以继续作为临时缓存或单次尝试日志，但不能作为全局配额、任务归属和权威结果的唯一来源。
数据库本身也需要持久卷、备份、恢复演练或托管服务；迁移数据库不是自动获得零数据丢失。

迁移接口应是 reserve_budget、claim_task、commit_operation 等业务事务，不能只包装 execute(sql)。
队列可评估 PostgreSQL 行锁与 SKIP LOCKED，状态变更与幂等响应必须同事务提交。
不承诺任意外部调用 exactly-once；网络断开后的真实调用结果仍可能未知。

## 6. 分层存储与发布

事务数据库：租户、权限、预算、任务、租约代际、操作状态、产物清单和必要审计。
对象存储：源码快照、补丁、测试日志、轨迹、检查点等大文件。
Redis（可选）：可重建的缓存、非权威限流辅助状态；不作为唯一预算和账单真相。
搜索服务（可选）：派生检索视图，丢失后能够由权威数据重建。

数据库与对象存储之间没有默认的原子事务。先上传不可变对象并核验内容，再在数据库事务中
发布清单；部分上传和未发布对象保持不可见并按规则回收。由持久 outbox 发布后续事件，消费方去重。
对象路径必须由服务端生成或严格校验，租户检查不能依赖路径前缀约定。
活跃 SQLite 备份使用 Backup API 等一致性机制，不直接复制一个可能不完整的 .db 文件。

## 7. 多 Sandbox 执行和调度

每个 attempt 使用独立工作区，不让两个 Agent 并发修改同一 checkout。
跨 Sandbox 通过授权 API、不可变产物引用和消息传递协作，不共享凭证或直接访问对方磁盘。
消息绑定 tenant/task/attempt/operation、租约代际、输入摘要、截止时间和协议版本。
旧 worker 即使恢复联网，也必须被控制面和可信执行入口拒绝继续提交；仅写一个 fencing 字段不能阻止物理副作用。

调度需要同时考虑租户并发数、模型请求速率、Token 预算、CPU、内存、磁盘、GPU 和镜像/工具能力。
准入层先保留预算与容量，再选择兼容 worker；公平队列避免单个租户填满全局资源。
每次资源分配有归属和租约，但超时只表示失联：未确认旧执行停止时，容量与预算进入待核实状态，不能盲目复用。
Kubernetes 可负责 Pod 放置和资源限制；Ray 可用于任务/Actor 调度，但逻辑资源声明不等于物理安全隔离。
Keel 仍需负责业务配额、租户公平性、验收与证据语义。

## 8. 无 Docker 时的推进顺序与验收

1. 先定义 Agent/Store/Artifact/Sandbox 插件契约和版本化错误语义；保留当前兼容实现。
2. 用本地进程/HTTP fixture 检查两租户越权、相同幂等键隔离、配额并发与旧租约拒绝。
3. 增加真实服务数据库适配和迁移，验证两控制端并发、重复领取、断连、重启、备份恢复。
   数据库服务不可用时标记未验证，不能用 mock 测试声称 PostgreSQL 通过。
4. 增加对象存储适配，验证半上传、哈希不符、跨租户读取、元数据发布失败和垃圾回收。
5. 增加资源预留和公平调度，测排队时间、锁等待、拒绝率、资源利用率与跨租户干扰。
6. 待运行环境可用后，再运行多 Sandbox 隔离、进程终止、出口绕过及跨节点故障测试。

不要预填“支持多少用户”的结论：固定负载、并发阶梯、持续时间和通过门槛后实测。
P95/P99、数据库锁等待、重复执行数、未知操作数与恢复时间应和通过率同时报告。
