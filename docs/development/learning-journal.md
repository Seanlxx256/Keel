# Keel / Compass 项目学习与决策复盘

最后整理：2026-10-21。后续持续追加观察、修正结论。

这是一份面向开发复盘和面试准备的长期记录，整理已有报告与项目讨论中重要的判断转折。
它不是逐条聊天存档，也不是完整项目成本统计；早期案例按主题组织，不补造发生日期。
“为什么这样想”记录的是可核查的决策依据与取舍，不把模型生成的解释当作事实。

## 怎么读、怎么维护

- **已观察**：日志、源码、测试或模型原始回答直接支持的事实。
- **已验证（有范围）**：指定检查通过；必须写清验证的是工具、流程、环境还是修复结果。
- **推测**：与证据一致，但未通过区分性检查排除其他原因。
- **待验证**：方案或评测已准备，尚无对应真实结果。
- **不支持 / 已撤回**：已有证据不足以支持原判断，保留更正原因。

阅读路径：先看“项目主线”，再选案例，最后看“面试讲法”和“下一轮记录模板”。
细节以链接的原报告和原始产物为准；后续结论不能覆盖旧失败和旧成本。
如果历史文档中的“待验证”已有后续结果，在本文件注明先后关系，而不是把旧文档当成当前事实。

这份文档与其他材料的分工：

| 材料                                  | 回答什么问题                                                 |
| ------------------------------------- | ------------------------------------------------------------ |
| 本文件                                | 我们如何发现问题、调整判断、选择下一步，有什么可迁移的经验？ |
| [实验工程手册](experiment-runbook.md) | 下次写脚本时该复用什么实现、遵守什么约束？                   |
| `docs/evaluations/`                   | 某次实验的输入、结果、成本和结论边界是什么？                 |
| `.keel/` 下原始产物                   | 日志、源码快照、模型回答、报告和哈希等证据在哪里？           |

**本文件是开发者维护的项目记忆。** 写进文件不等于 Keel 已自动检索或执行经验，更不等于模型权重学会了它。
只有被具体运行入口读取、核实适用条件并实际验证的经验，才能称为对应范围内的运行时能力。

## 项目主线：我们真正想解决什么

目标不是让模型多生成几轮代码，而是让 Issue 修复过程可执行、可检查、可中断恢复，并能说明为什么相信结果。
Keel 组织定位、规划、修改、验证、审计与失败恢复；Compass 提供代码检索与上下文服务。
两者应通过实际任务的质量与成本验证价值，不能仅用角色数量、工具数量、日志数量证明有效。

发展中的关键转折：

1. 从“模型说改好了”转向独立验收和审计。
2. 从“失败就再试一次”转向传递具体失败证据、保留历史与预算约束。
3. 从手工处理单次环境错误转向共享检查、适用条件和验证过的恢复动作。
4. 从“接入更多工具应当更好”转向检查实际调用、组件对照与因果归属。
5. 从“增加反思步骤”转向检验反思是否产生新证据、排除错误假设。
6. 从连续付费重跑转向冻结对照、离线诊断；无效的强制机制应能撤回。

## 重要案例

### K01 ｜自己宣布成功不够，要把验收权交给独立流程

**发生了什么：** 项目面对的风险包括提前终止、测试未跑、修改验收内容等。于是把职责拆开，并在独立执行环境中验证补丁，另做审计。

**为什么这样设计：** 生成修改的一方也能生成漂亮的完成说明；语言上的完成声明无法替代执行证据。测试结果与测试本身是否被篡改，是两类检查。

**经验与边界：** Docker 隔离、AST 检查、测试报告比对、突变测试抽样各自覆盖部分风险。通过有限测试不代表软件绝对正确；防作弊检查也不是对所有规避方式的证明。
SWE-bench harness 提供独立评分方式，不代表项目已经获得代表性的 benchmark 成绩。

**面试切入：** 为什么不让 Implementer 自测后直接结束？回答信任边界、职责分离和独立证据，而不只列六个角色。
参考：[项目评测协议](../evaluation-protocol.md)、[失败恢复与任务工厂](../autonomous-recovery-and-campaign.md)。

**角色机制澄清（2026-10-21，无新增实验证据）：** 代码核查确认六个职责阶段不等于六个独立常驻 LLM Agent。Agent 模式的 Scout、Planner、Implementer 使用独立 AgentSession/会话历史，但可共享同一个模型客户端；Critic 走独立的结构化恢复决策接口，Verifier/Auditor 主要是宿主确定性代码。实际 SWE-bench localized-proposal 模式里，Planner 阶段由宿主包装已定位目标为工作项，不一定另调一次规划模型。角色按状态机串行切换，Critic 提出 repair/replan/stop，宿主验证合法跳转、权限和预算；任务 DAG 描述工作依赖，不代表六角色并行。

当前没有统一可发现的“智能体卡片”实现；类似信息分散在角色提示、ToolGateway 权限、输出 schema 和状态机中。可准确讲“多角色工作流与隔离会话”，不能讲“六个独立服务通过 Agent Card 自主协商”。将来若统一卡片，应由同一配置生成提示和实际权限，并校验执行层一致性，不能把卡片声明本身当成权限隔离。参考：`keel/agents.py`、`keel/orchestration.py`、`keel/gateway.py`、`keel/runtime.py`。

### K02 ｜保护规则正确，反馈不具体，模型仍会反复撞墙

**发生了什么：** 首次 SymPy 16450 试验失败后，Scout 多次选择失败日志中的测试文件作为修改目标，但测试路径受保护。旧错误只说“文件缺失或受保护”，没有具体指出哪条选择违反哪条规则。

**怎么处理：** 返回实际越界路径，明确区分“失败证据所在文件”和“可写源码目标”，保留拒绝行为，不静默替模型挑选正确文件。

**为什么这样想：** 重试只有在反馈能改变下一次决策时才有意义。把无效选择静默过滤掉，会掩盖模型未理解约束的问题，也可能留下错误的编辑计划。

**证据范围：** 首次试验的失败与成本保留；回归检查验证了具体反馈和保护规则，不能单独证明新提示提高了真实修复成功率。
参考：[SymPy 首次失败复盘](../evaluations/sympy-16450-keel-trial-v1.md)。

**后续更新（2026-10-21，高预算探索再次出现）：** extended-v1 仅用 7 次调用、43,040 Token 就因相同定位错误停止，未开始修改。三次文件选择都含受保护测试路径，尽管宿主已两次明确指出错误；全局 400,000 Token 和 12 次恢复动作并未用尽。这说明早期经验虽已记录、错误提示虽已具体化，仍未变成足以约束模型输出的接口契约。

此次非分页 schema 仍允许任意字符串，分页才约束当前可选项。下一步应研究可读证据与可写目标的显式区分及目录选择约束，而不是继续加预算、过滤掉错误路径替模型做决定或关闭保护。完整目录枚举也可能增加上下文成本，因此需要先离线测量和回归验证；本轮尚未改生产选择逻辑。参考：[高预算结果复盘](../evaluations/extended-budget-exploration-v1.md)。

**通用接口修订（2026-10-21）：** 开发者把非分页文件选择也约束为实际可写目录枚举，已观察到但不在当前可写目录中的路径另列只读证据；纠错反馈独立展示。没有按 Astropy 路径写特殊分支，没有替模型过滤错误项，宿主仍完整拒绝违规选择。只读列不是读工具的额外限制，也不授予写权限。

79 项相关检查完成，77 通过、2 项可选检查跳过。离线重建旧请求的 33,213 字节与原 trace 一致；实际 510 文件目录的新请求分为 46,782 / 20,198 字节两页，均未超过原 48KB 上限。代价是一次合法选择可能从一调用变两调用，不能宣称降本；当前优先验证能否跨过协议阻塞。模型可能忽略 schema，因此只是接口与宿主约束检查通过，真实选对/修复仍待验证。参考：[选择契约与成本](../writable-localization-contract.md)。

补充检查：在配置好的虚拟环境运行 18 项定位契约/编排检查全部通过，包含真实 LangGraph 路径（使用模拟模型）。已准备新的 `.keel/repair-exploration/extended-v2/run.ps1`，沿用 mini、原失败源码、工具、验收与高预算，仅更改通用选择接口并绑定新实现哈希；旧 extended-v1 保留。没有启动第二次付费尝试，真实收益待用户终端执行后复核。

**真实结果更正（2026-10-21，extended-v2 已完成）：** 本轮跨过了早停并进入修改，但 schema 没有让模型完全遵守选项：仍有受保护/越页选择被宿主拒绝、纠正，不能宣布协议错误已消除。最后一轮前页选中 card.py，后页又舍弃它、改选工具模块；Implementer 仍试图修改 card.py，超出当轮证据与计划范围而被拒绝。这说明合法选项约束不等于相关性判断或跨页目标保持。不要通过放宽权限或按任务名固定文件来掩盖此问题。参考：[extended-v2 复盘](../evaluations/extended-budget-exploration-v2.md)。

### K03 ｜有日志不等于 Critic 收到了有用证据

**发生了什么：** 三任务初始批次只解决一题。报告中大量通过测试 ID 占据有限上下文，后续裁剪又让 traceback 细节消失。Astropy 的目标测试通过了，但回归测试失败，恢复环节拿到的信息不足。

**怎么处理：** 优先传递结构化失败测试、错误片段和当前差异，完整日志通过证据引用保留，而不是只截取标准输出尾部。

**为什么这样想：** 先判断信息是否真的到达决策者，再讨论模型推理是否不足。记录、检索、传输、模型可见是不同环节。

**证据范围：** 信息丢失有原报告支持；它是否是某题失败的唯一原因，没有证明。后续成功也不能反推所有收益均来自这一个修复。
参考：[初始三任务批次](../evaluations/swebench-new-task-batch-v1.md)、[恢复诊断协议](../recovery-diagnosis.md)。

### K04 ｜基础设施阻塞、输入错误和代码失败必须分账

**发生了什么：** 五任务批次中，Pylint 的 editable build 失败、Pytest 遇到 Windows 编码错误、Matplotlib 准备阶段无法重命名目录；另有实际 Agent 修复成功与失败。

**怎么判断：** 先定位执行到哪一层、是否生成有效测试报告、Agent 是否真正开始。不能把没跑起来算成模型修复失败，也不能从分母中悄悄删掉。

**经验：** 同时报告计划数量、实际执行数量、通过数量和不可用原因。`completed`、`graded`、`resolved` 描述不同状态。

**面试切入：** 如何防止评测数字失真？回答失败分类和分母，再谈成功率。
参考：[五任务结果](../evaluations/swebench-new-task-batch-v2.md)。

### K05 ｜环境恢复需要观察能力，也需要足够的合法动作空间

**发生了什么：** Pylint 的包装环境调整让安装继续，但参考测试仍失败。后续 ReAct 能检查模块和 distribution，却重复提出已试过的 recipe，或在允许动作不足时停止。

**为什么卡住：** “安装成功”不能排除运行时依赖不兼容；“断言失败”也不能直接证明包装工具有问题。模型知道下一步可能要查什么，不代表控制器支持这项检查或恢复。

**怎么设计：** 用固定诊断程序读取实际解释器、导入位置、版本和 entry point；恢复动作限定为数据化 recipe；同一 recipe 即使换了解释也仍是重复动作。需要新证据才能继续。

**边界：** 当前包装恢复不承诺修复任意网络、编译器、权限或项目依赖故障。`unsupported_scope` 是能力边界，不是环境健康证明。
参考：[有界环境恢复](../harness-environment-recovery.md)。

### K06 ｜同样叫“网络通了”，验证强度可能差很多

**发生了什么：** Matplotlib 的系统包安装长期阻塞。主机、容器、构建阶段对单个文件的下载成功，完整 apt workload 仍出现 502。随后隔离的 no-pipeline 策略下，工作负载完成。

**为什么逐层检查：** URL 可达、完整下载、构建路径下载和整套包管理器工作负载，是逐渐接近真实场景的检查。一个小探针通过，只能排除它覆盖的部分原因。

**保留的推测：** 工作负载在该传输策略下恢复，不足以唯一证明 HTTP pipelining 就是根因；瞬时网络、代理路径与时序可能同时变化。

**经验：** 恢复成功要由原工作负载验证。不要因 502 后出现“仓库未签名”就关闭签名校验；先看最早的真实获取错误。
证据入口：`.keel/network-checks/` 下的 `matplotlib-*` 记录；[实验手册](experiment-runbook.md)。这里总结的是已有会话与产物记录，引用具体数字前应定位相应原始报告。

### K07 ｜插件冲突应通过同输入对照确认，不应直接修改业务源码

**发生了什么：** Matplotlib SCM 诊断发现，同一版本策略有两个 provider：一个在 warning-as-error 下抛弃用警告，另一个在相同输入下正常返回版本。

**为什么这比猜版本更强：** 保持输入一致、只改变 provider，能区分“项目版本计算本身有错”和“额外插件抢占旧策略入口”等不同解释。

**怎么处理与标注：** 后续沿用经过参考验证的重建环境策略；不改业务源码或测试掩盖环境故障。即使恢复，结果仍要标明 reconstructed conditions，不能冒充原环境成绩。

**经验：** 找到一个能运行的配置和证明唯一根因是两件事。恢复动作要检查依赖者、作用范围，并重新跑参考验证。
参考：[保存源码续修验证](../evaluations/saved-source-repair-continuation-v1.md)中的环境说明；原 SCM 探针保存在 `.keel/network-checks/`。

### K08 ｜终端重启、解释器和凭据是运行条件，不是模型推理问题

**发生了什么：** 用户终端重启后，进程级 API key 不再存在；保存源码续修直到 Critic 调用才暴露缺少凭据，前置准备已经产生开销。终端使用的 Python 还来自另一个项目的虚拟环境。

**怎么处理：** 在昂贵准备和创建执行产物前检查凭据引用；检查真正被调用的解释器，不假定当前终端的 pip 对应运行中的 Python。配置脚本隐藏输入、配置文件不写明文 key。

**为什么这样想：** 认证不可能靠代码推理凭空恢复；需要用户提供的秘密信息与可自动检查的环境条件要明确分开。

**经验：** 日志记录解释器路径和“凭据存在与否”，不记录凭据值。终端中的环境变量不会自动共享给所有工具进程。
参考：[环境配置](../environment-setup.md)、[单任务入口](../run-swebench-task.md)。

**后续更新（2026-10-21，准备进度对照时）：** 默认系统 Python 未安装 MCP/LangGraph，原有虚拟环境两者均有。准备入口新增“启用 MCP 配置时检查宿主客户端包”，在付费运行前发现错误解释器；未执行的 `progress-v1` 保留且失效，改用原虚拟环境冻结 `progress-v2`。这是实际解释器检查的又一次应用，不是安装新依赖或模型自主修复的证据。

### K09 ｜只读工具也可能写缓存；声明不等于操作系统隔离

**发生了什么：** Serena 工具发现成功后，真实调用仍遇到语言服务器配置与 Windows 子进程清理问题。后续调用成功，但 `.serena` 配置和缓存写入又触发了编辑范围审计。

**为什么之前的判断不够：** “发现工具”“调用一次”“干净退出”“符合工作区写入约束”是不同验收层次。工具名或 read-only 声明不能证明没有磁盘副作用。

**经验：** 优先复用第三方 MCP 实现，以隔离环境解决依赖冲突；再检查真实 schema、服务配置、当前仓库工作目录、生命周期与缓存副作用。不要为了让集成过关而整体关闭源码审计。

**边界：** MCP 协议互操作不等于工具效果提升；独立环境也不是 OS sandbox。
参考：[Serena 接入过程](../serena-integration.md)、[外部工具治理](../external-tools.md)。

### K10 ｜工具可用、实际被调用和产生收益，必须分别证明

**发生了什么：** 可选 Compass 文本工具的配对试验中，两道完成的任务都通过了，两组 Token 有差异，但外部工具调用次数为零。

**调整判断：** 不能把成本变化归因于 Compass，也不能因为配置里列出了工具就写“Compass 提高修复效率”。需要先保存模型实际收到的工具目录、调用记录与结果交接。

**为什么这样想：** 在有工具的组里结果更好，只是配置级关联；工具根本没被使用时，不存在该工具直接贡献的执行证据。强制调用可以验证集成，却改变了实验问题。

**经验：** 接通协议、工具使用率、检索质量、完整任务质量分别评测。
参考：[可选工具首轮配对报告](../evaluations/compass-text-optional-v1.md)。

### K11 ｜索引一两个小时：先判断有没有进展，再决定是否继续

**发生了什么：** 检索验证长时间没有可读进度，中断后还可能重复计算。后来区分了文件解析、向量生成、提交、发布等阶段，并加入批次检查点与有界运行。

**为什么不只加长超时：** 活着不等于有进展，客户端超时也不保证 Docker 或远端请求立即停止。只在结束时写结果会丢失大量已完成工作。

**经验：** 心跳描述存活，计数增长描述进展，检查点描述已持久化成果，最终发布描述完整性。续跑前核实源码、模型、输入和配置身份，不能只看目录存在。

**边界：** 检查点恢复本身是可靠性收益，不是检索质量收益。部分向量已生成不代表完整索引可评分。
参考：[实验手册](experiment-runbook.md)、[Django 覆盖诊断](../evaluations/django-retrieval-coverage-v1.md)。

### K12 ｜同一个 WinError 5，可能不是同一种故障

**发生了什么：** 一类发生在进度 JSON 原子替换，一类发生在 CocoIndex named-pipe 通信。前者可能与短暂文件占用有关；后者通过实际解释器运行 server/client 小探针，观察到当前执行环境的传输权限边界。

**怎么区分：** 记录阶段、操作、解释器和最小复现，不根据错误码机械执行同一条修复命令。短暂占用可有界退避，持续权限问题不能无限重试或自行提权。

**经验：** 非关键遥测可明确降级，正式结果和向量检查点写入失败不能静默忽略。权限探针应在复制代码、加载模型和建索引前运行。

**边界：** 当前工具进程权限受限，不证明用户正常终端也受限。
参考：[外部工具恢复验证](../evaluations/external-tool-recovery-v1.md)、`compass/progress.py`。

### K13 ｜评测范围不匹配，应保留不适用，而不是修改题目

**发生了什么：** Python-only 检索遇到参考范围包含配置文件；Django 仓库还有刻意制造 SyntaxError 的测试 fixture；Xarray 的参考行区间无效。

**怎么处理：** 昂贵计算前检查题目与语料范围是否匹配。对于有效 Python 范围，制定一般化、可声明的新策略，而不是按仓库路径加特例。无效标签保留为输入失败，不手工修成好看的分数。

**为什么这样想：** 如果看到结果后改适用规则，实验回答的问题就变化了。可以做派生实验，但必须保留原规则、排除项和来源。

**经验：** 不适用、未运行和真实零命中不是一个状态。Django amended-scope 成功不代表原严格完整性要求通过。
参考：[覆盖诊断与派生策略](../evaluations/django-retrieval-coverage-v1.md)。

### K14 ｜原始字节、Git diff 与跨平台编码不是同一个概念

**发生了什么：** 上游 `.gitattributes` 的编码过滤导致工作区字节与 commit blob 相同，Git 普通洁净检查仍报差异。Windows 写 shell 脚本的换行也曾造成 `pipefail` 执行错误。

**怎么处理：** Git 检查仅在受限条件下进入原始字节比对；真实内容、模式、类型、删除和 symlink 变化仍拒绝。发给 Linux 的脚本明确使用 LF，避免用主机默认写法生成执行产物。

**为什么这样想：** 错误检查不能靠“关闭检查”解决。需要明确检查的对象和转换过程，再设计尽量窄的例外。

**边界：** `git diff` 空或非空不能单独替代所有内容完整性检查；测试 fixture 也不能依赖个人 Git 全局设置。
参考：[字节级快照验证](../snapshot-encoding-verification.md)、[实验手册](experiment-runbook.md)。

### K15 ｜检索平均分提高，不足以决定换默认方案

**发生了什么：** Code-aware 排序在三个开发任务上比 RRF 基线更好；但模型读码升级 T2 并未提高这些任务的召回。后续 reranking、融合及 Aider 原生排序组件对照中，又出现精确率、召回和逐题收益不一致。

**具体观察：** 四任务组件比较里，Compass 平均行精确率 38.25%，Aider 原生排序组件 8.00%；Aider 的平均召回更高。固定交替混合相对 Compass 一胜一平两负，不能只因平均召回提高就推广。

**为什么这样想：** 候选是否包含相关代码、排序是否靠前、100 行预算如何分配，是不同瓶颈。“更多 LLM”“更多候选”“更复杂融合”都可能挤掉有用内容。

**经验：** 同时保留候选覆盖、排序、上下文打包、逐题收益和成本。组件适配器不是完整 Aider / Serena 产品，开发集优势不是“胜过所有 Code RAG”。
参考：[三仓库策略验证](../evaluations/compass-final-policy-three-repo.md)、[Aider 互补性分析](../evaluations/aider-compass-complementarity-v1.md)。

### K16 ｜中断后继续修，需要的是状态与失败反馈重新接回执行

**发生了什么：** Matplotlib 的终端断开。保存工作区独立评分发现补丁不完整；环境与补丁应用已不阻塞，但评分不会自动恢复 Agent 会话。

**怎么处理：** 校验 task、参考环境、源码与补丁身份，把保存的源码、当前差异和真实失败报告作为新尝试输入；由 Critic、Scout 和 Implementer 自行诊断修改，不在运行时写 `_antialiased` 修复分支。

**已验证结果：** 后续一次续修通过官方评分：FAIL_TO_PASS 7/7，PASS_TO_PASS 89/89；8 次模型调用、37,388 Token。环境是参考验证过的重建条件；成本不包含此前开发和最终评分。

**边界：** 这证明一条通用续修路径在已知任务上完成过修复，不是恢复原模型会话，不是首次尝试成功率，也不能归因于未调用的 MCP 工具。继承补丁不自动获得追溯审计认证。
参考：[保存源码续修报告](../evaluations/saved-source-repair-continuation-v1.md)。

### K17 ｜“再读一点、再想一轮”可能只是在重复原假设

**发生了什么：** Astropy 14508 原目标测试已通过，但一个回归测试持续失败。简单续修组四次实际修改后，失败仍相同。分析发现修改反复围绕长度和格式回退，却未稳定验证格式化、科学计数法与验证路径的因果关系。

**提高问题层次：** 不再把“替这道题写正确代码”作为当前开发目标，而问：系统是否提出了可区分的原因？有没有执行能否定某个原因的检查？下一轮判断是否因观察而改变？

**为什么这样想：** 改动不同不代表认识进步；新增阅读行数不代表找到关键行为；Critic 写出“应检查调用链”不代表检查真的完成。需要把反思的语言输出与证据产生、决策更新分开看。

**边界：** 这道题历史上有通过记录，因此不能说 mini 必然不会做。当前观察支持流程不稳定，不支持唯一归因于模型能力或缺少向量记忆。
参考：[诊断检查复盘](../evaluations/diagnostic-inspection-review-v1.md)。

**后续更新（2026-10-21，进度对照后）：** 两组都通过工具读到了失败测试正文（fact 14，2000..2055 行）。实验组 Scout 随后却把测试总结为“保留不规范字符串”，没有区分先正常写入、再人为改坏、最后检查警告三个阶段。因此不能简单归因于没有找到源码；应区分“读取到”“交接到”“解释对”。这是契约理解的证据，不是已执行根因实验，也没有把具体答案写进 Keel。参考：[进度试验复核](../evaluations/recovery-progress-pilot-v2.md)。

### K18 ｜我们自己增加的机制，也必须接受撤回

**发生了什么：** 多个 Astropy 开发版本加入强制诊断、目标定位和缓存阅读等机制。部分修好了真实上下文交付缺陷，但实际修复没有稳定成功。

**付出的成本：** 六个选定历史尝试共 553,140 Token、114 次模型调用尝试，包含连接/基础设施错误。它们版本不同，不是因果对照，也不是项目累计全部成本。

**受控对照：** 同一保存源码、模型和预算下，简单组花 156,074 Token、30 次调用，四次中间验证；强制检查组花 68,107 Token、13 次调用，未进入修改。两组最终都失败。后者便宜来自提前停下，不能称为保质降本。

**怎么调整：** 默认关闭未证明收益的强制诊断，保留可选实验入口、普通失败反馈、预算、审计和已有较优候选保留。先做小评测，再决定是否加回。

**核心经验：** 自我改进也包含简化和撤回。不能因机制理论上合理、合成测试通过，就持续叠加并让用户为验证不足付费。
参考：[对照结果与工程决定](../evaluations/diagnostic-inspection-review-v1.md)。

### K19 ｜保留较好候选是风险控制，不等于学会修复

**发生了什么：** 多轮修改可能破坏原来已经通过的测试。加入按相同测试集合比较候选、保存源码字节和失败时恢复的机制。

**已观察：** 上述简单组四个候选评分都为“一项回归失败、零项目标失败”；同分保留早期候选，最终源码哈希确认恢复到种子。

**为什么这样设计：** 允许探索，但不能只因最后一轮最新就交付它。候选评分必须在相同验收集合下比较，缺失结果或不同测试范围不能假装可比。

**边界：** 恢复旧补丁不会把运行状态变成成功。相同失败数量只是当前保守排序规则，不保证语义上完全同样好。恢复机制验证通过不代表修复效果提升。
参考：[诊断对照中的 checkpoint 验证](../evaluations/diagnostic-inspection-review-v1.md)、`keel/repair_checkpoints.py`。

### K20 ｜开发者看得到，不等于角色下一轮看得到

**发生了什么：** 诊断模型找到目标并读过源码后，后续请求只看到搜索命中和旧事实索引；重复读请求又被去重，原正文没有重放。模型因此不断说缺少实现细节。

**怎么处理：** 在有限上下文中重放相关缓存源码正文，保留原 fact ID 和来源哈希；明确哪些正文省略。缓存重放不伪装成新读取，也不重置无进展计数。

**为什么这样想：** 去重减少成本，但若只去掉工具调用、不补回已有结果，会让恢复流程失忆。应按角色实际收到的消息检查上下文，而不是只看全量账本。

**证据范围：** 离线重放和回归检查验证了交付；没有单独证明模型因此能修好 Astropy。
参考：[诊断上下文复盘](../evaluations/diagnostic-inspection-review-v1.md)、[实验手册](experiment-runbook.md)。

### K21 ｜更好的小测分数，也可能没有验证我们关心的问题

**发生了什么：** 历史诊断把自然语言句子交给字面搜索，六次零命中。我们先做六例工具协议对照：原提示 4/6，候选 6/6，12 次模型调用、2,954 Token。

**重新解释：** 两组对五个存在的目标都搜到了；差异在两次对“零命中是否证明不存在”的布尔回答。于是撤回“该小测证明修复了历史搜索失误”的解读，不把 4/6→6/6 宣传成代码修复提升。

**为什么这样想：** 评测指标可能混合多个能力。先拆开失败项，判断测试是否真正触达目标瓶颈，再决定推广提示。

**下一步，待验证：** 已准备四例、两对相同症状不同根因的多轮诊断评测。模型先预测两假设下的结果，自选固定探针，读取真实执行结果，再给结论。猜对但没有有效区分性证据不能通过。
这只是封闭假设、固定探针的小评测，不是自由设计实验或完整修复能力；截至本次整理，还未检查到真实 mini 结果，不能写成成功。

参考：[诊断评测设计与已有搜索结果](../evaluations/diagnostic-inspection-review-v1.md)、`examples/evaluate_diagnosis.py`；搜索原报告在 `.keel/repair-review/search-guidance-model-v1/report.json`。

**后续更新（2026-10-21，真实 mini 结果已复核）：** 诊断小测原提示 2/4、候选 4/4；分别消耗 3,068 / 4,698 Token、6 / 8 次调用。八组首个检查都选对了，预测也正确；原提示两组把探针名 `original_failure` 当成证据 ID，被协议验证拒绝，未执行检查。其余六组执行后都得出正确结论。已核对 manifest、实现哈希、八份完成收据、重算评分和十四份原回答。

因此，本次差异主要表现为引用协议合规，不能称为因果诊断能力翻倍，也不是降本。候选提示未部署。下一项应分离协议纠正与诊断引导，在相同反馈机会下检验新案例；如果纠正引用后两组都通过，就不支持诊断提示本身带来收益。

### K22 ｜“记下经验”和“系统自主学习”之间还有工程距离

**当前区分：**

| 层次           | 做了什么                                                       | 不能因此宣称什么                   |
| -------------- | -------------------------------------------------------------- | ---------------------------------- |
| 当次任务反思   | 根据日志、差异、历史动作调整下一步                             | 已跨任务学会、已提高泛化能力       |
| 运维经验存储   | 部分入口保存已注册动作、环境签名、结果与证据，并按适用条件恢复 | 所有入口都接入、任意未知故障都能修 |
| 文档与候选经验 | 开发者整理规律，准备提示或策略候选                             | 运行时已自动调用、经验已验证有效   |
| 持久策略改进   | 需要开发/验证隔离、版本、独立对照和回退                        | 本项目已完成在线学习或模型训练     |

**为什么不先上向量库：** 语义相似只能找到候选经验，不能证明当前解释器、版本、权限与根因相同。先解决经验结构、适用性核实和验证，再决定检索方式。

**监督角色的边界：** Critic、Verifier、Auditor 有不同职责；多个角色可能使用同一个模型，不能当作独立专家投票。权限、预算、证据身份与独立验收由宿主执行，诊断语义仍可能错。

**经验：** 应保存触发条件、区分方法、恢复范围、验证标准、失败尝试和版本，而不是“看到错误 X 就执行命令 Y”。新经验先是候选，通过相似但不同任务验证后再考虑推广。
参考：[Compass 学习边界](../compass-feedback-learning.md)、[运维恢复验证](../evaluations/external-tool-recovery-v1.md)。

### K23 ｜不是没有目标，而是目标到每轮证据的闭环还不完整

**本轮问题：** 用户提出，是否因为缺少目标设定和监控，Critic 的努力方向分散。

**已核实的实现：** runtime 要求非空 goal，校验任务 DAG 和依赖。Critic 输入包含原目标、当前计划、失败反馈、源码差异、近期动作和诊断，并明确“修复原问题且保留既有被测行为，全部验收命令通过”。宿主监控预算、权限、角色阶段、重复失败；可选诊断检查另有目标定位与无进展保护；候选保留按同一测试集合的回归失败、目标失败排序。

**不足：** 普通恢复路径的 next_check 仍主要是文本，由下一角色按指令执行；没有统一的结构化记录把“本轮待解决的问题 → 竞争假设 → 检查预测 → 实际观察 → 假设更新 → 验收差异”全部绑定。写过检查建议不代表执行过；DAG 阶段推进、阅读行数或新补丁也不等于修复更接近完成。

**为什么这样区分：** “没有目标”与源码不符，但“只有远目标、缺少可验证中间目标”是合理的设计缺口。方向分散可能与此有关，还可能涉及证据交付、上下文、工具协议和错误假设；目前没有消融证明其中一个是主因。

**下一步构思（未实现）：** 沿用原验收不变，为每轮指定一个证据问题，而非硬编码答案。例如“区分序列化阶段已产生非法值，还是验证阶段误拒绝合法值”，把检查结果交接给 Critic；无新证据时改变假设或止损，不只换一段解释。过程指标不可替代最终验收，也不应成为新的强制层，除非小型对照证明收益。

证据：`keel/recovery.py::decide`、`keel/runtime.py::critic_phase`、`keel/repair_checkpoints.py::verification_score`、诊断小测原报告。面试讲法：“已有任务目标和结果验收，正在补足可核验的中间证据闭环；未把它宣称为已验证的自主规划改进。”

**后续更新（2026-10-21，开始接入，不宣称闭环已完整）：** 开发者新增默认关闭的 `recovery.monitor_progress`，SWE-bench 入口对应 `--recovery-progress`。复用现有 Critic 的 next_check 作为本轮问题，宿主绑定随后出现的文件/符号事实和新验收收据，再把有界清单交给下一次 Critic；终止时也保留未完成轮次的情况。沿用原验收与预算，不增加角色、模型调用或停止门槛；输入上下文增加，真实 Token 成本待测。

同一测试集合下报告候选改善、退步或持平；无匹配新验收收据就标记未重新验证。系统不因“读了源码”就宣布检查执行或假设成立，语义状态保留未验证。这是证据交接与观察基础，不是已完成自动假设检验、更不是持久学习。57 项相关检查运行完成，55 通过、2 项因可选 LangGraph 未安装跳过；包含模拟模型的多轮本地修复。尚未发起真实 mini/Docker 对照，不能写成成功率提升。参考：[恢复进度机制](../recovery-progress.md)。

**下一项可证伪检查：** 在新冻结的同模型、同预算对照中，区分提示输入增加与真实效果；记录 Critic 是否实际引用后续证据、是否改变无效方向、最终验收与总费用。若只是输出更长但修复不改善，应继续关闭默认或简化，而不是继续叠加监督角色。

### 常见追问与答题边界

- **“是不是多几个 Agent 就更可靠？”** 职责隔离有利于权限和审计；实际推理质量需要对照，不由角色数量保证。
- **“你们的 reflection 是不是学习？”** 当次任务适应和持久策略学习分开；目前不能称为训练模型或全面跨任务自学习。
- **“Compass 超过开源方案了吗？”** 只有特定任务、固定预算和组件配置下的指标；Aider 有更高平均召回的观察，不能概括成全面胜出。
- **“为什么还需要人为查日志？”** 某些缺口在动作空间、证据传输或入口集成；把已理解的问题变成通用实现和可验证经验，但未知故障仍可能超出能力范围。
- **“怎么证明不是 hardcode？”** 生产逻辑不包含具体 Issue 的答案分支；规则表达一般约束，并通过不同路径/不同案例验证。评测 fixture 的预置答案用于评分，不送给修复模型。
- **“有没有 Keel 带来的整体提升百分比？”** 当前材料不支持统一数字；组件试验、配对成本、开发通过记录分别报告，不能混成一个成功率。
- **“最重要的一次失败是什么？”** 可讲强制检查消耗更低却没有修复，说明必须同时看效果、停止原因与成本，而不是挑一个好看的数字。
