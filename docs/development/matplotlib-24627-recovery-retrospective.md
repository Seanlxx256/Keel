# Matplotlib 24627：从环境阻塞到自主纠错验收通过

日期：2026-10-24。本文针对 `matplotlib__matplotlib-24627`，不把此前 Astropy 14508、Matplotlib 25775 的实验混入本任务成绩。依据是保存的日志、冻结配置、源码补丁、官方报告和学习日志；不是对模型内部思维的还原。

## 1. 原始目标及验收边界

任务要求 `cla()` / `clf()` 清理对象时，也解除被移除 Artist 的 `.axes` / `.figure` 父引用。原始示例中，`line.remove()` 后 `line.axes` 为 `None`，而 `axes.cla()` 后仍保留旧 Axes 引用。

我们希望 Keel 自己定位、修改源码、运行测试，并在补丁失败后依据反馈继续修正。开发者负责通用编排和工具能力，不把本题的具体源码修法写进系统。

先跑参考补丁的目的，是确认环境能够执行官方验收。参考补丁只进入评分侧，不交给求解模型。参考验收通过不等于 Agent 修复通过；容器构建完成、命令退出码 0、外层 watchdog passed 也均不等于任务通过。

## 2. 实际经历的阶段

### A. 最早阻塞是系统依赖下载，Agent 尚未开始

初始参考构建在 Ubuntu APT 安装阶段退出 100，约 550 秒，日志显示连接 `archive.ubuntu.com` 失败。Matplotlib 的实例构建包含 TeX、ffmpeg、ImageMagick 等较大依赖链。其他任务跑通过，不代表这一套冷环境已经准备好。

当时已有网络探针、有限 ReAct 和 no_pipeline 实验能力，但参考评分失败没有自动接入它们。缺口首先是“能力存在，但主流程没有调用通道”。

因此增加 `reference_network_recovery`：绑定原任务、镜像 ID、脚本和失败证据，先有限重试原 APT，再进行允许的诊断/传输实验，最后重新跑官方参考验收。没有跳过依赖或替换任务，也没有修改签名校验、主机代理或参考标签。

### B. 恢复运行又暴露了超时清理问题

network-v1 在镜像 FROM 解压阶段停留，尚未进入 APT。内层 600 秒之后没有按时返回，直到外层 1800 秒终止。它不是第二次 APT 下载失败。

代码检查和进程实验发现：仅杀直接子进程，不能确保持有 stdout 管道的后代结束；读线程和管道 close 仍可能阻塞。现场未捕获精确阻塞栈，所以不能断言这就是 Docker 当时停滞的全部原因。但旧实现的清理缺陷可以独立复现：2 秒内层超时拖过 12 秒外层控制。

通用修复包括：直接写日志文件并有限轮询，避免依赖阻塞管道读线程；Windows 使用受控 Job Object，在派生工具前完成归属，终止本次进程树；POSIX 使用隔离进程组；内外层都有明确状态收据。新真实后代进程测试约 3.156 秒返回，心跳停止。没有把本地 CLI 清理等同于 Docker daemon 侧任务已清理。

### C. 有些运行确实在进展，却被统一时间上限截断

后续运行已经下载约 434 MB，还在解包安装时达到 600 秒。这里的主要问题从网络错误转为预算与冷安装阶段不匹配。

解决思路不是无限加时，而是“软分配 + 新进展续期 + 不变的硬截止时间”。识别新的下载、解包、配置里程碑；重复日志、计时增长、普通心跳不算进展；始终预留最终评分时间。

第一次进度策略仍不完整：v3 的 APT RUN 已在约 832 秒完成，但导出镜像层、解包镜像仍需要时间。解析器只认识包安装进度，在 960 秒把后续阶段截断。再补充 BuildKit export/unpack 阶段识别和一次性有限静默宽限，仍受原硬截止时间约束。

这两次失败也说明：观察到“进程活着”不足以续期；观察到“APT 完成”也不足以声明整个镜像构建完成。

### D. Docker/WSL 本身也出现过故障

期间出现 Docker API 不响应/500、代理到虚拟机 no route，以及 `wsl -l -v --all` 超时，用户重启 Windows 后恢复。证据支持 WSL/后端状态异常，但不能确定是内存、磁盘、驱动、死锁或 Keel 负载导致，更不能证明 Keel 直接停止了 Docker。

这与更早的 VHD 文件 WDAC 权限问题是不同事件，不混用旧根因。恢复后先做零模型的 info、本地镜像、短构建检查，再继续长实验。终端重启后丢失进程级 API key，也由凭据预检拦在付费请求之前。

### E. 网络通了、探针成功，也不代表原工作负载已经恢复

v5 原 APT 与 no_pipeline 实验分别约 517/570 秒后退出 100，虽然已下载大量文件。网络诊断有 3 次模型调用、9,446 Token，但没有恢复官方参考环境。

之后改为定位最新失败日志中的精确 URL，而不是随便选择一个曾成功的包。HTTP/HTTPS 配对下载得到相同内容，不能支持“换 HTTPS 一定解决”。

再引入受限 `retry_acquire`：APT 原生有限重试和连接超时、归档保留及缓存观测，保持原安装任务。完整工作负载约 800 秒完成，缓存从 0 增至 389 个文件。

重要限制：成功日志没有实际重试事件，不能断言这次成功就是 retries 参数的因果效果；也没有旧缓存命中证据，不能声称靠缓存复用解决。能确认的是，在该声明策略下完整工作负载完成了。

### F. 真正跑到测试后，又暴露依赖兼容性问题

参考评分命令完成，但官方结果仍失败。主要证据包括 SCM 版本方案的 DeprecationWarning，以及 pandas 对 NumPy 的要求不匹配。

只读检查发现两个问题：

- SCM 插件存在冲突 provider；`vcs-versioning` 的旧方案入口触发弃用错误，而原 `setuptools-scm` provider 可以正常工作。
- 安装的 pandas 与 NumPy 1.25.2 不兼容；需要通过当前元数据和解析器寻找受限调整，而不是凭经验写一个版本号。

实现零模型、有限范围的兼容性恢复：检查真实发行包元数据，验证插件是否可安全移除；固定 provider 和其他包版本，仅允许解析相关 consumer；禁止改项目 editable 包、测试/构建工具和未批准的新包；安装后检查 anchor 与新增依赖冲突，最后重新跑官方参考验收。

第一版选择范围有 bug：把环境中全部历史冲突都纳入，得到 8 个 consumer，触发最多 3 个的保护。正确改法是修“相关性筛选”，不是抬高上限：把失败栈模块映射到发行包，再与声明冲突相交，排除已由其他动作处理的插件，保留无关基线问题。

第二版由解析器两轮选择出 pandas 1.5.3，保持 NumPy 1.25.2；移除经验证无依赖的冲突插件。约 22 分钟、0 次模型调用，新的官方参考结果为：1 项目标测试、776 项回归测试通过；原始 pytest 为 777 passed、64 skipped。

这时才确认重建环境具备任务验收能力。它不是原始条件成绩，也不是 Agent 代码修复成绩。

### G. Agent 首次进入源码修复，但自己的补丁破坏了初始化

GPT-5.4 从原始源码出发，修改 `_base.py` 和 `figure.py`。候选在 clear 路径读取尚未存在的 `self.child_axes`，而此路径也会在 Axes 构造时执行，引起大范围 AttributeError。

第一轮独立官方评分：目标测试 0/1，回归 50/776 通过。原始 pytest 729 failed、50 passed、54 skipped、8 errors。这是候选补丁缺陷；环境策略已传递，不能再归因于先前 pandas/SCM 故障。

### H. 为什么没自我纠错：30 分钟外层里还有一个 10 分钟内层

配置沿用了 pilot 的 `--max-agent-seconds 600`。完整验收计入 Agent 时间，首次验证耗尽内层约 606 秒；只调用了模型 4 次、29,756 Token，远未耗尽调用和 Token 预算。

外层 1800 秒只是兜底终止，不会把剩余时间自动拨给 Agent。内层停止后仍做独立最终评分，整体约 18 分钟。因此这一轮不能证明模型“拿到失败证据仍修不好”，它根本未进入后续 Critic 修复轮次。

这也是开发者预算配置的问题。通用修复是共享单调时钟截止时间：扣除准备耗时、预留最终评分和清理时间，剩余时间分给 Agent；最终评分也接收实际剩余时间。新试验内层总计 1780 秒、外层 1800 秒，预留最终评分 600 秒；不再独立卡 Agent 600 秒。

### I. 首次完整自主纠错成功

agent-v2 仍从原始源码开始，不携带 v1 补丁或人工诊断。第一版候选仍失败，但这次流程有时间接收反馈：

1. Verifier 返回当前测试错误。
2. Critic 根据 AttributeError 选择重新规划。
3. Scout/Implementer 再检查源码并修改。
4. 第二次验证通过。
5. 之后独立官方评分也通过。

结果：1/1 目标、776/776 回归通过；10 次模型调用、79,497 Token、33 次工具调用。Agent 约 827 秒，整体约 17 分钟。审计只发现两个声明源码文件变化，未报告越界改动；该审计本身不是所有安全性质的证明。

这证明本次自主纠错闭环实际执行过，而非只有提示词建议。不过两个独立运行存在模型输出差异，不能把前后全部提升归因于预算这一单变量。

### J. 冻结版本复测：2/3 通过，暴露另一类协议恢复问题

冻结成功版本的实际源码、配置和输入，预先安排 3 次独立 fresh-base 运行。不按成功与否中止或替换样本。

| 样本 | 官方结果 | 验证轮数 / 纠错动作 | Token | 总耗时 |
|---|---|---|---:|---:|
| 1 | 1+776 全通过 | 2 / 1 | 80,114 | 约 17 分钟 |
| 2 | 无有效候选、无官方测试结果 | 0 / 2 次补丁纠正 | 40,619 | 约 3 分钟 |
| 3 | 1+776 全通过 | 3 / 2 | 133,880 | 约 21 分钟 |

样本 3 除初始化问题外，还根据 Artist 跨 Figure 归属异常再次修正，然后通过。说明不仅存在一次偶然闭环正例，但尚未达到稳定成功。

样本 2 的根因不同：模型的 old 替换文本在 figure.py 匹配到两处。连续两次没有消除歧义，触发本地重复失败保护。当时全局时间、Token 和调用额度都未耗尽。报告用 budget_exhausted 包装该停止，不能读成“30 分钟用完”。

由于没有候选，导出空补丁，官方 harness 跳过实例；桥接器又把缺少逐实例报告包装为 grading_error。主要失败是补丁定位恢复，评分错误是次级分类问题，不是 Docker 故障或测试不通过。

三次合计 32 次模型调用、254,613 Token、约 41 分钟。统计仍是预定样本中 2/3 官方通过；不能排除样本 2 后写成 100%。

### K. 把含糊错误变为可行动反馈，再小预算验证

旧反馈只说“匹配 2 处”，模型没有获得哪些位置发生冲突的直接提示。新通用反馈提供实际当前源码的行列、有限相邻上下文、未展示匹配数量，要求把不变上下文加入 old/new，形成唯一替换。仍禁止默认选第一处或批量替换；整批验证后才写文件。

同时消费已有 export receipt：空补丁直接记录 unresolved / skipped_no_candidate，保留原失败、官方分数为 null，不进入评分制造二次错误。

先用真实保存请求和源码做零模型复现，再进行一次 GPT-5.4 调用。反馈明确指出 figure.py 的第 177、952 行。模型扩大了替换上下文，两项 old 文本都变为唯一匹配，通过生产补丁验证。消耗 1 次调用、5,606 Token，约 20 秒。

这次只证明协议纠正，不证明生成补丁通过测试，更不能覆盖或替换稳定性样本 2 的历史失败。后续 agent-v3 完整流程测试是单独新实验；本文编写时只观察到 dispatching，没有结论。

## 3. Root cause 不是一个，而是分层的

| 层 | 已确认的缺口或现象 | 修复原则 |
|---|---|---|
| 外部网络 | APT 实际连接失败 | 精确失败 URL、受限实验、完整工作负载及参考验收 |
| 进程生命周期 | 内层超时无法保证后代/管道按时结束 | 真实进程树测试、受控 Job、无阻塞日志路径 |
| 主机环境 | WSL 管理和 Docker 后端异常，具体原因未确认 | 独立健康检查，保留诊断，必要用户恢复，不编造根因 |
| 进度调度 | 正在安装或导出却被固定软限额终止 | 有证据的有限续期，覆盖完整阶段，硬截止不变 |
| 依赖兼容 | SCM provider 冲突和 pandas/NumPy 不兼容 | 元数据驱动、最小 consumer 调整、fresh reference gate |
| 恢复作用域 | 一度把全部历史冲突都当目标 | 失败证据关联选择，不靠抬高上限绕保护 |
| 预算架构 | 外层 30 分钟与内层 10 分钟互相独立 | 共享截止时间，显式预留验收和修复机会 |
| 模型候选 | 初始化次序/父对象生命周期判断不完整 | 测试证据驱动重新定位和修正，由模型写源码 |
| 补丁协议 | 重复片段定位不明确且错误反馈不可行动 | 当前匹配位置和上下文，保持唯一匹配及原子校验 |
| 结果报告 | 无候选被误报成评分故障 | 无候选、基础设施、真实测试失败分别分类 |

## 4. 关键方法及反思

- 先问失败发生在哪一层、哪一阶段，再决定下一步。环境没好之前，不能给模型源码能力打分；源码候选破坏初始化后，也不能继续归咎环境。
- 将 Observation 转换成具体下一步动作，而不是只加反思文字。对确定性问题，元数据、解析器、校验器和进程控制比多加一个角色更直接。
- 测试“本地通过”需要说明层级。单元测试、真实子进程测试、Docker 工作负载、参考验收、Agent 官方验收，是不同证据。此前简单 fixture 没覆盖现场后代进程或复杂历史依赖噪声，这些失败反过来改进了测试集。
- 预算不只是成本控制，也决定系统是否有机会纠错；但更多时间本身不能修复连接错误、错误作用域或错误补丁。
- 保留唯一匹配、作用域和审计保护，不为了让本题通过而宽松应用补丁。要提升的是模型收到的信息质量和编排接续能力。
- 冻结实际成功源码，而不只是记住“曾经通过”。独立复测暴露了此前看不到的补丁协议短板；失败样本不删除、不重标成绩。
- 复用完成的环境和证据，做小预算 checkpoint 实验，再做完整集成。一次 20 秒的协议回放适合验证反馈是否可用，但不能冒充完整修复成绩。
- 这是开发者迭代了系统、模型在单次运行中适应了反馈，不等同于模型参数学习，文档也不会自动变成 Keel 的运行时长期记忆。

## 5. 当前可陈述的成果与边界

可以陈述：实现受限环境恢复和 fresh reference gate；修复进程生命周期与共享时间预算；GPT-5.4 在该公开任务上完成实际失败反馈后的源码修正并通过官方验收；冻结后 3 次独立复测有 2 次通过；一个剩余协议失败已在一次小预算回放中消除。

不能陈述：通用环境永不失败、所有问题根因已确定、模型长期学习了经验、稳定 100% 修复、原始环境条件成绩、未接触任务/跨仓库泛化已经证明，或 agent-v3 已成功。
